# UltimaAI 任务工作流范式

> **G-TASKFLOW-001（2026-10-29 用户明确批准建立）**：Ultima 全系所有任务的**处理与下发工作流**统一采用本范式。执行端（Codex / DeepSeek / 未来任何模型 API）只是可替换的**执行适配器**，替换入口**不改变**工作流本体；任何任务必须走同一套「登记 → 计划评审 → 执行 → 独立审计 → 有界修复 → 验收 → 冻结」流程，禁止绕过工作流裸跑。

> 版本：v1.0 ｜ 状态：批准生效（2026-10-29 Owner 拍板）｜ 适用范围：Ultima 全系产品（UltimaAgent / UltimaConsole / UltimaManager / UltimaSentinel / UltimaScan / UltimaRadar / UltimaGold / UltimaEngine / UltimaAdmin 等所有挂 Ultima 前缀项目）及后续新项目
> 唯一权威源：`H:\UltimaAI\_shared\paradigms\UltimaAI-任务工作流范式.md`（镜像：ultima-docs-repo `docs/shared/`）
> 依据：本范式由 UltimaManager 工作流（plan → plan review → develop → audit → bounded repair → approval → frozen）实战验证后固化；执行端调用细节见 [Codex-外部执行端调用范式.md](Codex-外部执行端调用范式.md)（当前默认执行端适配器）。

## 0. 定位与核心思想

| 层 | 是什么 | 可变性 |
|---|---|---|
| **工作流本体**（本范式） | 任务从登记到冻结的全生命周期流程、门禁、状态机、容量、越界保护 | **固定**（跨产品、跨执行端统一） |
| **执行适配器** | 实际执行任务的模型/工具入口（Codex CLI、DeepSeek API、未来模型） | **可替换**（替换不影响工作流） |
| **交互端** | 用户 / 豆包主脑：澄清目标、登记工单、验收决策、Owner 拍板 | 人 + 主脑 |

**三条铁律**：

1. **工作流固定，执行端可变**：无论入口是 Codex API Key、ChatGPT 网页通道、DeepSeek API，还是未来任何模型——任务下发、执行、审计、验收、冻结的流程与门禁完全一致；只有「执行适配器」参数（命令形态/模型名/凭证）不同。
2. **先读规范再动手**：任何开发/审计/同步动作前，先读根 INDEX + 本范式 + 目标项目 INDEX，再动工单；派发 prompt 首段强制引用。
3. **规划、开发、独立审查分离**：计划评审与独立审计必须由独立会话执行；只有人类能完成原规定的 Owner 验收、冻结和发布批准。

## 1. 任务生命周期（标准状态机）

每个任务（工单）走以下生命周期，状态不可跳级：

```text
待登记 → 已登记(待派发) → 计划评审(plan review) → 执行中(develop)
   → 独立审计(audit) → [REVISE 有界修复 → 重新审计] → 技术验收通过
   → [需要批准: approval inbox] → Owner 验收 → 冻结(frozen) → [发布: 另行门]
                    ↘ 阻塞(blocked) → 修复或人工处置
```

| 状态 | 含义 | 进入条件 | 出口条件 |
|---|---|---|---|
| 待登记 | 需求已提出，未成工单 | 需求澄清后 | 工单三段式完成 + 全局主表登记 |
| 已登记/待派发 | 工单合规，等待派发 | DoR 五项全绿 | 执行适配器派发 |
| 计划评审中 | 只读规划器产出 DAG，独立评审批准 | 派发后第一阶段 | 独立会话批准 exact plan digest |
| 执行中 | 开发会话运行 | 计划评审 PASS | 回执 + 验收证据齐备 |
| 审计中 | 独立审计会话运行 | 执行完成 | 独立审计 PASS / REVISE |
| 有界修复 | REVISE 后的修复会话 | 审计 REVISE | 修复完成 → 重新独立审计 |
| 阻塞 | 失败/越界/缺证据/缺批准 | 审计 FAIL / 缺回执 / 越界 | 修复闭环或人工放行 |
| 冻结 | 技术验收 + Owner 验收完成 | Owner 拍板 + 冻结 tag | 仅发布门可继续 |
| 发布 | 公网/移动端/签名安装 | 冻结后另行决策 | 单独门，不代签 |

**硬约束**：

- **一任务一进程**：一张工单 = 一次执行会话 = 独立进程/会话，禁止"一包多单"；工单内部 T0→Tn 在该会话内顺序执行。
- **Gate PASS 才进下一步**：每个 T 有封闭验收清单，全绿才过；"预计通过"不算通过。
- **技术阶段通过 ≠ 冻结**：冻结必须 Owner 拍板 + 实际冻结 tag；审计 PASS 不代表 Owner release。

## 2. 计划评审（规划与执行的分离门）

1. 工单派发后，**只读规划器**产出任务 DAG（有向无环图，含任务边界/依赖/写域/验收）。
2. **确定性策略校验**拒绝：
   - 未批准或 Owner-HOLD 的目标；
   - 错误的修订号 / 不安全或重复的任务身份；
   - 环或图外依赖；
   - 超过批准上限的任务数；
   - 写域超出批准根目录；
   - 验收覆盖被缩减。
3. 规范方案哈希后持久化；**独立的计划评审会话**收到 exact 方案，必须返回 PASS 且 digest 完全一致，才物化 `develop` 与 `audit` 阶段。

> 效果：规划与执行分离、方案不可被执行端偷改、依赖必须先通过才推进。

---

## 3. 执行（develop）

- **fresh 会话**：每次执行全新进程/会话，精确项目 cwd、每阶段写根、来源指纹、持久预留、证据目录、PID 与进程创建身份。
- **执行适配器**（可替换）：调用已安装执行端可执行文件/API，参数化 argv，`shell=False`，拒绝命令解释器（cmd/PowerShell/shell 脚本）。
- **凭证隔离**：子环境移除通用 provider 凭证与 Owner 能力；prompt 经 stdin 传递，不入安全会话回执。
- **来源 CAS**：成功的已验证内部写入 CAS 工单来源哈希并推进所有仍就绪的串行兄弟（继承先前已接受的变更）；外部编辑永不重新贴标签。
- **派发前再校验**：预留与每次 spawn 前重查项目归属/暂停、目标修订/批准/HOLD、工单与阶段 scope、依赖、预留 token、实时项目指纹。

---

## 4. 独立审计与有界修复（audit / REVISE）

1. 每次执行后进入**独立审计**会话（只读沙箱，fresh 身份）。
2. 审计按验收清单逐条核验：验收命令实际跑通、证据路径存在、越界声明属实、来源未漂移。
3. 审计结论：
   - **PASS**：进入技术验收通过；
   - **REVISE**：同一阶段进入**有界修复**（默认上限 2 次），携带 exact 任务契约 + 先审意见，修复后返回 fresh 只读审计；
   - **FAIL / 阻塞**：持久化不可运行状态，不自动续跑。
4. 验收命令约束：每个启用的产品适配器携带 1–16 条有界验收命令（argv 数组、shell=False、现有可执行文件、cwd 在精确项目内、超时 1–1800 秒）；cmd/PowerShell/shell 脚本等解释器一律拒绝。

---

## 5. 批准门（approval inbox，人工门）

- 需要人工批准的运行：持久化一张**收件箱卡片**，绑定项目/工单/阶段/请求步骤/动作/修订/来源哈希/影响范围/证据/有效期/幂等键。
- **决策一次性**：批准决策在共享派发锁内校验当前归属/暂停、目标修订/批准/HOLD、动作转移、实时文件哈希、状态/有效期/精确行 CAS；错项目/过期/变更来源/重复/并发失败者拒绝。
- 批准的 resume **只**改变被绑定的等待阶段并唤醒调度器；**不**扩展写域/重试/发布权，不绕过依赖、容量、来源、测试、资源检查。拒绝/修订保持不可运行阻塞态。

## 6. 容量与并发（WIP 上限，全系统一）

| 维度 | 上限 |
|---|---|
| 全项目合计执行中 | **≤2**（全项目执行进程安全线） |
| 每项目执行中 | **≤1**（同项目不并发，防抢改同批文件） |
| 全项目独立审计/计划评审 | **≤1** |
| 修复（REVISE） | 默认 ≤2 次/阶段 |

调度排序：优先级 → 最近未派发项目 → 阶段创建序 → 复合身份。容量同时计入内部运行/预留与导入的外部/未知执行者；未适配的共享登记执行中/审计行按外部未知执行者占用容量。

## 7. 越界保护（fail-closed 哨兵，C2 级）

**每个关键写入前必须校验授权写域；任一差异路径无任何授权覆盖 → 拒绝执行（fail-closed）。**

1. **授权登记**：任何对项目文件的写入（代码/配置/队列/报告/证据/工单）必须有已登记的授权 scope（精确文件路径；仅证据目录等明确场景可用目录级）。
2. **合并写域判定**：越界判定合并全部已登记授权 scope 后判定；任一差异路径无任何授权覆盖仍抛冲突——**不是**"有任一授权即放行全部"。
3. **授权完整性校验**：授权 scope 与 pins scope 必须一致；缺授权 = 越界。
4. **审计发现缺口 → 补追认授权**：合法后续开发若超出既有授权，须登记追认授权（`retroactive_registration=true`）再复核全部差异路径覆盖，禁止静默改哨兵。
5. **哨兵正确拦截 ≠ 环境失败**：fail-closed 触发说明"当前快照与正式授权登记不闭合"，是真实缺口，须补登记闭环，不能忽略。

> 实战验证：2026-10-28 UltimaManager 自审计即由哨兵拦截未登记写域（报告/证据/新工单）→ 补 v29 授权 → 全量复绿。此机制证明"工作流能自我纠错"。

## 8. 执行适配器（可替换层）

| 适配器 | 用途 | 切换动作 |
|---|---|---|
| **Codex CLI**（当前默认） | 登录版 `codex exec`，`-m gpt-5.6-sol` | 按 [Codex-外部执行端调用范式.md](Codex-外部执行端调用范式.md) 执行；更换版本/模型即更新该范式 §1/§8 |
| **Codex API Key** | `sk-proj-*` 通道 | 凭证入加密 vault；命令形态换 API 调用，工作流不变 |
| **DeepSeek API** | 未来接入 | 新增适配器登记（模型名/命令/回执格式），工作流不变 |

**切换规则**：

1. 切换/新增执行适配器 = **只改适配层**，不改变本范式 §1–§7 任何流程、门禁、容量、越界保护。
2. 新适配器必须满足：可独立进程/会话执行、支持参数化输入（stdin/请求体）、可产出标准化回执（§9）、凭证不入仓。
3. 适配器变更后更新 [Codex-外部执行端调用范式.md](Codex-外部执行端调用范式.md)（或新增对应调用范式）并走范式登记（存档总纲）。

## 9. 回执必报（执行端 → 派发方）

每次执行完成（无论成功/阻塞/终止）必须返回标准回执：

| 字段 | 说明 |
|---|---|
| 工单号 | 追踪标识 |
| 执行端 | 谁做的（Codex / DeepSeek / …） |
| 完成状态 | 已完成 / 阻塞 / 已终止 |
| 根因结论 | 问题根因一句话（诊断类必填） |
| 产出路径 | 改动文件 + 报告 + 证据目录 |
| 验收证据 | 构建/测试/命令输出摘要 |
| 越界声明 | 无=明确写"无"；含未动范围 |
| 环境声明 | 模拟器 vs 真机；未验证必须写"仅预期"，禁止冒充已验证 |

**阻塞必报而非伪造**：执行端遇到无法完成的 Gate（越界/缺授权/证据失真）必须如实报阻塞，禁止伪造 PASS 或静默跳过。

## 10. 冻结与打 tag（铁律，全系默认自动）

1. **冻结门**：阶段报告产出 → AI 复核 → 冻结 tag（`stageN-frozen` / `vX.Y.Z` / `wo-<id>-frozen-<date>`），未冻结不进下一阶段/不宣称完成。
2. **打 tag 铁律**：每个关键修改/更新完成即打 git tag（版本冻结/阶段冻结/工单闭环/关键修复），tag 与 commit 一一对应、可解析可回滚；完成即自动打 tag 并推送（本地仓库无远端时至少打本地 tag），**无需逐次询问确认**。
3. **缺 tag = 闭环未完成**：回执/报告宣称"已完成/已闭环/已冻结"时对应 tag 必须存在（`git tag -l` 可查）。
4. 冻结语义：功能与技术验收门全部闭合 + Owner 拍板；**部署/发布/签名安装/公网开放/移动端仍为独立门**，不因冻结自动通过。
