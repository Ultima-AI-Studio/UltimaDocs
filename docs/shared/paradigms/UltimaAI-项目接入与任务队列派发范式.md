# UltimaAI 项目接入与任务队列派发范式

> 版本：v0.2；日期：2026-10-28。
> 状态：G-DISPATCH-001 自主推进版已由用户于 2026-10-28 明确批准生效（取代 2026-10-24 Manager 唯一调配版）；其余新增接入细则仍为待复核草案。不追溯改写历史回执或活动契约。
> 本地权威候选：`H:\UltimaAI\_shared\paradigms\UltimaAI-项目接入与任务队列派发范式.md`。
> 依据：既有 Codex 调用范式、顶层架构标准、项目 INDEX、用户 2026-10-28 拍板的管理模式调整，以及本聊天批准的隔离、审计、自主推进和人工门要求。

## 1. 适用范围与权威分工

### G-DISPATCH-001：各项目自主推进开发（调用 Codex，遵守规范队列）

**各项目自主推进开发，由项目方直接调用 Codex 执行，不再要求经 UltimaManager 统一入队、准入和调配。** 覆盖全部现有和后续项目，包括 Manager 自身。自主推进不等于脱离规范：工单三段式、DoR 五项、全局主表登记、WIP 上限、冻结门、打 tag 铁律与回执必报必须遵守，禁止绕过规范裸跑。Manager 保留为可选监督/审计工具，不阻塞产品推进。

控制面规则记录和提案不是产品开发准入。原工单、写域、验收、预算与 Owner 门继续约束各项目，不能由"自主推进"推导出无限开发权限。

本文件统一描述"项目如何接入规范、任务如何登记入队、何时可以派发、如何验收接续"。不提供可绕过规范的直接执行命令，不改变模型权限、系统权限或原验收。

| 信息 | 权威来源 | 其他载体的职责 |
|---|---|---|
| 项目目标、精确写域、验收和禁止项 | 已批准方案、原工单及其来源绑定的阶段契约 | 索引负责定位，界面负责呈现 |
| 谁能派发和恢复 | 各项目方自主派发；授权、暂停状态与规范底线约束 | 观察器和监督者不得自行争夺派发权，也不得阻断项目自主派发 |
| 已登记的执行状态 | 各项目 `tasks\queue\` 主表 + 全局主表 + 实际进程身份、持久会话、退出和验收回执交叉验证 | Markdown 主表与 JSON 镜像聚合展示，不反向授权 |
| 尚未登记的遗留执行状态 | 原控制器与持久回执，仅供只读核对及交接 | 不再独立派新开发；规范补登记后才由项目方准入 |
| 人工批准、最终验收和冻结 | 明确的人类决定及原规定证据 | 策略建议或独立技术 PASS 不能代签 |

`Codex-外部执行端调用范式.md` 保留为执行端调用依据。其历史路径、模型可用性和命令示例不是当前机器的能力证明；每次使用应核对实际执行器和正式契约。不得为了入队扩大沙箱权限或跳过审批。

## 2. 项目接入清单

接入前逐项记录，缺项保持只读或说明阻塞，不能默认补为通过：

1. 固定 `project_id`、项目根路径、`docs/INDEX.md`、原方案和工单索引。
2. 核对项目与能力注册，避免重复项目、路径别名或把临时工作树误作新项目。
3. 列出原控制器、恢复器、定时任务和正在执行的进程；记录 PID 与创建身份。
4. 排他交接执行权，明确观察、派发、恢复各由谁负责。已有活动执行不能靠删除共享锁或重启进程腾出槽位。
5. 保全旧任务、失败、额度、已批准决定、受保护成果、版本和原暂停标记。
6. 固定控制器、权威文件、写域、版本身份及必要资源的证据；精确文件与目录写域应分别表示。
7. 在本项目队列和全局主表登记原工单身份。已有原单新增阶段应挂回原单，不能换单号重置历史。
8. 只有真实核验通过后，才能由各项目方自主准入并派发；登记项目、导入旧状态或显示“已接管”均不等于产品验收通过。

维修候选或执行端迁移可以采用独立管理上下文，但必须显式指回原产品和原工单，并保留其原门。候选准备通过不授权安装、许可接受或生产切换。

## 3. 工单与上下文身份

下列是审查清单，不是可直接提交给 API 的请求体，也不是允许手工改正式数据库的说明。

| 分组 | 必须能核对的信息 |
|---|---|
| 项目与目标 | `project_id`、项目根、`goal_id`、批准目标及类别 |
| 原单与阶段 | `original_work_order_id`、阶段标识、任务标题、前置依赖、来源版本 |
| 单次执行 | 独立 `run_id`、新会话、实际模型和推理配置、执行器身份、PID 与创建身份 |
| 来源与范围 | 当前源码指纹、批准时来源、精确可写路径、只读上下文和受保护文件 |
| 验收与证据 | 固定输入与期望、实际命令、环境、退出、报告和持久证据位置 |
| 授权与预算 | 授权种类、策略版本、原单累计消耗、重试冷却、人工门及暂停 |

关联、刷新选中项和定位任务应使用完整 `project_id / original_work_order_id / stage_id / run_id`，不能仅按标题、工单名或 Run 标识关联不同项目。

每个执行进程只承接一个明确原单的有界阶段。规划、独立计划复核、开发、独立审计各使用新进程/会话；不得把多个项目的提示词、可写根和历史混在一个执行上下文中。当前阶段引用前序结论及证据指针，避免复制整个工作区或秘密数据。

## 4. 入队与派发前检查

### 用户明确补充：范式未更新，不引导新请求入队（2026-10-24）

- 项目 INDEX 须定位 G-DISPATCH-001、G-WO-NAME-001 与本接入范式，并明确项目内申请/工单目录及 Manager 唯一控制权。缺失、过期或存在独立派发冲突时，仅登记待范式更新，不引导提交新队列请求或默认纳入扫描。
- 完成文档更新后，仍由 Manager 核验项目接管、原单身份、授权、来源、依赖、累计预算、暂停和 Owner 门；不能只靠字符串命中取得准入。
- 重读队列先做只读快照与正式记录对账。重复请求挂回原单；疑似废弃、冲突、被替代项记录建议和依据，在核验及适用批准前不删除、不移动、不改写其历史状态。
- 新请求接入条件与已有契约分别核验；禁止批量清除原契约、运行/失败回执、预算、暂停和人工门，也不凭此补充自动恢复旧任务。
- 此补充是用户指定的控制面引导规则，不代表定时目录扫描、自动导入或程序级接入门已经部署。其实现与存量迁移仍统一走 Manager 管线。

1. 原单和全局登记存在；任务标题能说明具体要交付什么，类别和优先级可辨识。
2. 目标仍在批准范围内；契约摘要、来源、文件/目录身份与当前状态一致。
3. 前置验收、冻结、资源及人工门满足；仅缺资源的任务不能通过标记“就绪”排除阻塞。
4. 固定模型、真实推理要求与执行器可用；`high` 不能冒充原要求的 `ultra`。
5. 累计预算、退避与冷却允许本次动作；换阶段名不重置原单消耗。
6. 项目暂停、Owner HOLD、旧硬停止和跨项目条件接续仍受检查。
7. 每项目执行中不超过 1，全局真实执行不超过 3，独立审计不超过 1。按实际命令、角色和身份判断，不能仅凭进程名计数。
8. 使用共享工程锁，在正式登记事务与比较更新中再次核对条件和幂等性。锁文件存在不是“锁已失效”的依据，禁止删除共享锁抢派。
9. 由各项目方创建持久 run 后启动新执行（自主派发 Codex）。只有真实执行进程与会话证据齐备才显示“执行中”；仅生成提示词或启动请求不算派发成功。

入队成功与立即开工分别呈现：可以已登记、等待调度，也可以因依赖、暂停、预算或资源待放行。界面必须保留具体等待原因。

## 5. 执行、验收与独立审计

标准阶段关系为：

`登记 → 就绪检查 → 规划 → 独立计划复核 → 开发 → 配置验收 → 独立审计 → 阶段通过或有界修复`

- 开发退出 0 只证明进程正常结束；还需有效回执、无越界、真实配置验收以及独立审计。
- 审计为 REVISE 时，即使进程退出 0，也显示“要求修复”，不能显示验收通过。
- 有界阶段 PASS 不能替代整单、真实设备、双通道、覆盖率或 Owner 冻结等原门。
- 保留失败回执和来源快照。新阶段以可信接受血缘接续，不把旧失败改为 PASS。
- 构建与测试使用隔离临时数据库、密钥和锁；运行中的桌面程序使用新临时构建输出，不能为了测试停止后台任务或覆盖被占用的正式产物。
- 开发环境受限的失败必须保留；需要正常 Windows、真实设备或其他指定环境验收时，以对应真实回执为准。不得删测、增加跳过或弱化安全来制造通过。
- 修复轮次必须有授权与原单累计预算，修复后重新独立审计。预算耗尽或真正人工边界进入待人工，不改阶段名继续消耗。

阶段通过后仍需检查下一阶段的来源、前置与控制权；不能因为有空闲槽位就启动未经检查的工单。

## 6. 自主动作与人工边界

仅在项目已接管、目标已批准、策略版本及能力真实生效后，才能按该项目策略自动裁决。各项目预算以其正式策略和累计记录为准，不把某一工单的额度复制给所有项目。

| 情形 | 处理 |
|---|---|
| 可信运行时证明的暂时网络故障 | 在原策略预算、退避和身份检查内有限重试 |
| 普通退出 1、缺回执、工具文本自称网络错误 | 先分类和核对，不当作可信网络事实 |
| 已发生部分源码写入 | 先独立检查点、范围和目标诊断，再决定是否能续行 |
| 身份未知或进程仍在 | 等待或核实；不重复派发或结束新同 PID 进程 |
| 认证失败、支付/额度、新资源、保护源变化 | 明确边界，停止盲试 |
| 目标内建议、修复或重规划 | 来源绑定、确定策略检查及累计预算允许后才执行 |
| 改目标、改原验收、后来 Owner HOLD、最终冻结/发布 | 保留人类门，不由策略代签 |
| 已明确保留为人工批准的安装、许可或生产切换 | 提交具体版本、影响、权限、回退方案，获得相应批准后再执行 |

自动动作的正式记录应带策略版本、`actor=delegated_policy`、项目/原单、依据、范围、来源和真实消耗；不能伪装成 Owner 的批准。批准必须绑定具体方案及来源，不能把用户一次选择扩展成所有项目的永久权限。

## 7. 观察与状态展示

- 顶部全局执行区显示实际项目、原单、具体阶段、run、进程身份及时间；不受当前项目列表筛选影响。
- 区分等待、准备启动、执行、待审计、要求修复、阻塞、待人工、验收通过、取消、被取代和历史关闭。
- 缺身份、失联或旧快照显示“待核实”；不得使用递增“已运行”时间制造仍在执行的结论。
- 连接失败或数据过期时明确标注快照。刷新间隔和过期阈值以实际实现为准，不假定所有项目都已有同一界面能力。
- 只展示必要的运行元数据、安全摘要与证据位置，不暴露凭据、完整提示词、推理内容或敏感工具输出。

## 8. INDEX 接入与变更纪律

根入口为 [UltimaAI INDEX](../../INDEX.md) 的导航链接；既有[启动入口](../启动入口.md)、[存档总纲](Ultima-范式存档总纲.md)继续保留各自职责。

新项目 `docs/INDEX.md` 应定位本地权威接入文档、原工单索引、全局主表、自主派发规范及人工门，避免复制范式正文。项目副本或镜像不能反向覆盖权威文件。

已有项目的 INDEX、工单或范式若被活动契约绑定哈希，先登记链接更新意图，待安全窗口按本项目管线复核后再改；不能为加入口而使正在执行的来源失效。

除已获用户批准的 G-DISPATCH-001 自主推进版外，其余新增接入细则须经相应评审与批准后才能标为生效。原验收和 Owner 门继续有效。文档编写完成、纳入索引或程序包含相关代码，均不等于原生策略引擎已经部署验收通过。
