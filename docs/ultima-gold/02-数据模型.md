## 3. 索引与唯一约束汇总

- orders.tx_hash UNIQUE（订单幂等验收 = 同 tx_hash 落单数 1 条；重复插入报 IntegrityError）
- push_tasks.msg_id UNIQUE（推送成功率分母按 msg_id 去重）
- users.email / users.invite_code UNIQUE
- audit_logs(created_at) 索引；orders(user_id,status) 索引

## 4. 订单状态机

```
pending ──收到 tx_hash──> confirming ──区块深度达标(TRON≥19/EVM≥12) 且 连续确认≥4轮──> confirmed ──对账通过──> settled
     │                        │
     └──超时/无效──> failed（终态）
```
- 状态仅链上确认模块独占推进（唯一写入口）
- 财务对账：sum(orders.amount) 按 chain 分组，与财务汇总精确相等 diff=0（6 位小数）

| 表 | 域 | 用途 |
|---|---|---|
| kline | market | tf ∈ m1/m15/m60 等；open_time 为 epoch 秒；m1 由 mt5_feed 常驻 2 秒更新（行情新鲜度门读取源） |

### 状态机（运行版 payment_orders，UGP-03 止血保持）
```
pending ──回执提交(receipt/manual/callback/poll)──> submitted（等待核验，不开权益、不发回调）
pending ──链上核验(onchain，UGP-16 前未实现)──> confirmed ──> callback_status: success/skipped/failed
pending ──expire_stale_orders 超时──> expired
```
- 仅 `source='onchain'` 可写 confirmed；任何路径不自动 settled（对应 v2.35 §4 状态机的运行版落地）。

## 6. UGP-08 数据模型登记（版本化迁移 + 来源标签）

> 依据：`backend/ultima_backend/db.py`（唯一迁移权威）+ `repositories/`；表结构变更统一走显式可重跑迁移，版本记录于 `schema_version`。

| 新增表/列 | 位置 | 说明 |
|---|---|---|
| `schema_version(version PK, name, applied_at)` | 业务库 | 迁移版本记录；同版本只应用一次（可重跑） |
| `migration_exceptions(id, tbl, issue, row_key, created_at)` | 业务库 | 迁移一致性校验异常隔离表（不修改业务行，不悄悄丢账） |
| `orders.source`（TEXT DEFAULT 'test'） | orders | 来源标签：live / test / legacy_unverified；存量打标：is_test=1→test，其余→legacy_unverified（仅首次加列时执行一次，幂等） |
| `payment_orders.source`（TEXT DEFAULT 'test'） | payment_orders | 同上；存量一律 legacy_unverified（旧 confirmed 不自动升级为真实资金证明）；新订单默认 test，链上核验（UGP-16 后）才可 live |

- **live 营收/链上核验计数口径**：仅 `source='live' AND status='confirmed'` 计入（repositories.live_revenue / onchain_confirmed_count）；legacy_unverified 与 test 一律不计入。
- **回执路径写 source='test'**：confirm_payment_order 的 receipt/manual/callback/poll 分支 UPDATE 附带 `source='test'`（UGP-03 止血口径不变；onchain 分支保留占位）。
- **迁移回退规则**：回退必须先处理切换后增量，禁止直接恢复旧库覆盖新交易（任务卡完成标准；本轮未执行实际库回退，机制登记）。

## 7. UGP-17 数据模型登记（M004 支付幂等与金额分配）

> 依据：`backend/ultima_backend/db.py` SCHEMA_VERSION=4，`_m004_payment_idempotency`（缺列才加、索引 IF NOT EXISTS，幂等可重跑）。

| 变更 | 说明 |
|---|---|
| `payment_orders.idempotency_key`（TEXT） | 幂等键（下单请求唯一）；同键只允许一张订单 |
| `payment_orders.amount_units`（INTEGER） | 最小单位整数金额（资产注册表 decimals 解析套餐价 + 唯一尾数） |
| `payment_orders.asset_key`（TEXT） | 资产键 `chain@network:contract/mint`（定位金额归属链） |
| `payment_orders.allocation_key`（TEXT） | 分配键 `收款地址\|asset_key`（金额槽位占用查询） |
| 索引 `idx_pay_idem`（部分唯一） | `idempotency_key` 非空唯一 → 同幂等键并发/重试单订单 |
| 索引 `idx_pay_alloc`（部分唯一） | `(asset_key, receive_address, amount_units)` 在 pending/submitted/confirming 活动态内唯一 → 活动金额分配唯一（撞分配返回忙） |
| 新表 `payment_order_exceptions(id, order_no, reason, tx_hash, created_at)` | 可审计异常队列：过期/晚到账/少付多付/缺金额/终态重复回执（不自动发权益） |

- **状态机补充**：`pending → submitted`（仅回执线索）；`submitted` 为待核验活动态（金额槽位仍占用）；异常/终态（expired/cancelled/exception）不占用金额槽位、可被新订单复用。
- **幂等与分配保证**：进程写锁（`payments/orders.py _ALLOC_LOCK`）+ DB 部分唯一索引双保险；同幂等键并发由 `idx_pay_idem` 兜底（IntegrityError → 回滚回查幂等返回同一订单）。

## 8. UGP-18 数据模型登记（C4 ChainEvidence 与链上核验）

> 依据：`backend/ultima_backend/payments/verification.py` + `payments/chains/*.py`。ChainEvidence 为**服务端验证产生的可信证据，仅此可推进到账状态**。

| 实体 | 说明 |
|---|---|
| `ChainEvidence`（内存对象，`to_dict()` 供落账层消费） | `{order_no, tx_hash, chain, network, asset_key, amount_units, from_addr, to_addr, block, block_time, confirmations, finality}`；`asset_key='chain@network:contract/mint'` 与资产注册表一致 |
| 核验结果状态 | `confirmed`（深度+连续确认 ≥4 轮通过）/ `pending`（深度不足或轮次不足，待更多确认）/ `rejected`（资产/链/收款方/金额/成功状态/时间窗/唯一性任一硬核对失败） |
| 确认轮次状态 | `ConfirmationTracker`：`(block_ref, ts)` 序列；block 回退/重组 → 撤回重置；同 block 或时间未前进 → 不计新轮；累计 ≥4 → confirmed |

- **深度门参数（验收参数，不视为任意链永久最终性保证）**：TRON≥19、EVM(ETH/BSC)≥12、SOL 按最终性（confirmationStatus confirmed/finalized）。
- **唯一性约束**：`tx_hash` 已绑定其他订单 → 拒绝（`_unique_event_ok`，跨订单复用证明禁止）；DB 侧后续由 UGP-19 加链事件唯一约束。
- **状态机衔接**：`submitted`（待核验）→ 核验 confirmed →（UGP-19 落账层推进 confirmed/fulfillment）；rejected/pending 不改变 submitted 活动态（金额槽位仍占用，等待更多观察）。

## 9. UGP-19 数据模型登记（M005 outbox 与账务）

> 依据：`backend/ultima_backend/db.py` SCHEMA_VERSION=5，`_m005_outbox_and_ledger`（建表 IF NOT EXISTS + 索引，幂等可重跑）。

| 表 | 关键约束 | 语义 |
|---|---|---|
| `payment_events` | `event_id UNIQUE`；`UNIQUE(order_no, event_type)`；`status ∈ pending/delivered/failed/dead`；attempts/max_attempts(8)/next_retry_at | 出站事件 outbox（PaymentVerified）：event_id 为回调幂等键；同订单同事件类型只入队一次；失败有界重试+退避，超限 dead |
| `payment_ledger` | `tx_hash UNIQUE`；`order_no` 索引 | 账务记录（链事件唯一约束）：同一证据重放不重复入账；记录 chain/network/asset_key/amount_units/block/block_time/evidence_id/event_id |

- **落账事务边界**：payment_ledger 写入 + payment_orders→confirmed（仅 pending/submitted/confirming 活动态，`source='live'`）+ 事件入队在同一数据库事务；网络回调（deliver_callbacks）在事务外独立执行。
- **状态三分**：`payment_status`（orders.status）≠ `callback_status`（事件状态）≠ `fulfillment`（权益应用，pending/retry_required；done 由 UGP-27 写入）——confirmed 不等于权益已开通。
