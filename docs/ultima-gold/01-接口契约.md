## 1. Web API 通用约定

- Base URL：`https://<domain>/api/v1`（沙盒：自签证书本地域名）
- 鉴权：`Authorization: Bearer <token>`（登录签发；后台另有管理员角色）
- 响应封装：`{ "code": <int>, "msg": "<string>", "data": <object|null> }`
- 错误码见 11-枚举数值总表.md；`code != 0` 即失败
- 分页：`?page=1&page_size=20`，返回 `data.total`
- 删除类接口：**不提供**（删除仅管理员人工，无 API 端点）——对应"删除类物理禁入"

## 6. 引擎→主服务信号传输接口（跨机，CHG-001）

- **传输方式**：消息队列（引擎机 → 主服务机）；禁止直连数据库跨机读写
- **消息体**：`signal_msg{signal_id, ts, type, params_snapshot, model_version?, fixture_id?}`
- **可靠性**：消息确认（消费后 ack，失败重投 ≤5 次，退避 2/4/8/16/32s 同推送口径）；引擎机心跳 topic（间隔 30s，丢失 3 次触发主服务降级）
- **验收**：断线重投不丢信号（机器判定）；心跳丢失触发降级日志

## 7. UGP-06 公共契约登记（C1–C6，backend 拆分单份权威）

> 依据：`H:\TuppoAU\backend\ultima_backend\contracts\__init__.py`；拆分范围见 `docs/reports/UGP-06/diff.md`。
> 原则：**业务逻辑单份**——`news-feed/feed_server.py` 保留 init_db/路由/后台线程并逐函数薄委托到 backend；任何域函数只在一个模块实现，禁止复制第二套。

### C1 时间契约
- 库内时间统一 `YYYY-MM-DD HH:MM:SS`（本地时区）；`now_iso()` 为唯一生成入口（contracts）。
- 订单过期时间 = 下单时刻 + `payment_config.ttl_minutes`（默认 30 分钟），格式同上。

### C2 金额契约
- 金额单位 USDT，两位小数；**对账容差 0.005**（`confirm_payment_order` 金额校验）。
- 订单金额唯一性：`金额 = 套餐价 + 随机一位小数尾数（0.1–0.9）`，撞单自动避让（防对账撞单）。

### C3 标识规则
- `user_id`：`U + 秒级时间戳 + 3 位数字`（查重循环保证唯一，UGP-06 修复同秒碰撞缺陷）。
- `order_no`：`PAY + 秒级时间戳 + 4 位随机数字`（存在即重抽）。
- 邀请码：6 位大写字母+数字（查重循环）。

### C4 状态常量（payment_orders 状态机）
```
pending ──回执提交(receipt/manual/callback/poll)──> submitted（等待核验，不自动开权益）
pending ──链上核验(onchain，未实现前不放开)──> confirmed
pending ──超时(expire_stale_orders)──> expired
confirmed ──> callback_status: success/skipped/failed（出站回调，HMAC-SHA256 签名，重试≤5）
```
- **UGP-03 止血（保持）**：仅 `source='onchain'` 可写 confirmed；该流程未实现（UGP-16 前占位），故任何路径都不会自动 settled。

### C5 错误响应对（contracts）
- `ok_data(data)` → `(200, {'code':0, 'data':...})`；`err(status,msg)` → `(status, {'code':status,'message':...})`
- `ok_legacy(data)` → `(200, {'ok':True, 'data':...})`（管理后台）；`err_legacy(status,msg)` → `(status, {'ok':False,'error':...})`
- `shape_of(obj)` 识别 `{code,data}` / `{ok,data}` 双形，供网关/测试复用。

### C6 授权响应形状（兼容基线，必测覆盖）
- 注册/登录：`(200, {'code':0, 'data':{'user':{user_id,username,email}, 'token':..., 'inviteBind':...}})`；错误密码 `(401, {'code':401,'message':...})`
- 管理后台登录：`(200, {'ok':True, 'data':{'token','name':'Ultima Admin','role':'admin'}})`
- `resolve_admin_token` → `{name,email,role,accountId:'admin'}`
- S 前缀写路由（`ADMIN_ONLY_POST_PREFIXES` 21 条）未带 token → 401（UGP-03 鉴权门保持）。

## 8. UGP-08 版本化迁移与唯一业务数据库契约

- **唯一迁移权威**：`ultima_backend.db`（`db.py`）是业务库（SQLite）表结构变更的唯一入口——建表/补列/种子一律以显式、有序、可重跑迁移表达（版本记录于 `schema_version` 表）；`feed_server.init_db` 内嵌建表逻辑保持为基线初始化，末尾挂 `apply_migrations(conn)`。
- **接口**：
  - `db.connect(path)`：业务库连接工厂（唯一数据库入口，默认行工厂，兼容既有 tuple 访问）。
  - `db.apply_migrations(db, target=None, migrations=None)`：应用未记录迁移（幂等可重跑）；单迁移事务内执行，失败回滚且不记录版本 → 抛 `MigrationError(version, name, cause)`（可定位可重跑）。
  - `db.applied_versions(db)` / `db.ensure_schema_version(db)` / `db.SCHEMA_VERSION`（当前=1）。
  - `repositories.link_checks(db)` → `[(table, issue, row_key)]`：迁移后一致性校验（金额/关联），空列表=一致。
  - `repositories.isolation_report(db)`：异常写入隔离表 `migration_exceptions` 并返回报告；不改业务行（不悄悄丢账）。
  - `repositories.live_revenue(db)` / `onchain_confirmed_count(db)` / `legacy_unverified_count(db)`：live 口径统计（仅 `source='live' AND status='confirmed'` 计入）。
- **来源标签（source 列，orders/payment_orders）**：`live`=链上核验通过（真实资金证明）；`test`=测试/未核验占位（新订单默认）；`legacy_unverified`=迁移前存量（旧 confirmed 不自动升级为真实资金证明）。回执路径（receipt/manual/callback/poll）写 `source='test'`（UGP-03 止血口径不变）。
- **偏离登记（PostgreSQL → SQLite）**：任务卡写"PostgreSQL 业务仓储"，但 UGP-05 冻结 feed_server 纯标准库零第三方依赖、业务库即 SQLite `news.db` → 以标准库 SQLite 等价实现版本化迁移语义（迁移表/版本 tracking/事务重跑/来源标签），不引入 PostgreSQL 依赖；行情库 `data/xauusd.db` 独立保留不在迁移管辖。

## 9. UGP-17 可幂等订单与回执受理契约（C3 PaymentIntent 幂等版）

### 下单（C3 幂等）
- 输入：`product_ref='tuppoau'` + `chain` + `idempotency_key`（必填）；价格/精度/网络/收款地址一律由服务端权威库回，客户端无价格参数入口。
- 主体：可信会话（user/admin）或有效商户凭据；**无效商户 key 拒绝（不回退官方站）**。
- 幂等：同一 `idempotency_key` 重复/并发/超时重试返回同一订单（不生成多笔待支付）；不同键各自独立订单。
- 金额：最小单位整数（`amount_units`），由资产注册表 decimals 解析套餐价 + 唯一尾数（0.1~0.9 最小单位，活动窗口内该收款地址金额唯一）；**无槽位返回"金额槽位已满，当前忙"（含"忙"），不扩大随机伪装成功**。
- 落库：`payment_orders` 新列 `idempotency_key/amount_units/asset_key/allocation_key`；部分唯一索引 `idx_pay_idem`（同幂等键单订单）、`idx_pay_alloc`（活动金额分配唯一）。
- 入口：`ultima_backend.payments.api.create_payment_intent_endpoint(db, token=, merchant=, api_key=, product_ref=, chain=, idempotency_key=, plan_id=, receive_address=)`；委托 `payments.orders.create_payment_intent`。**feed_server 现有 `/api/pay/*` 端点委托接线登记为下次重启落地点**（不破坏运行中官网支付）。

### 回执受理（仅提交线索）
- 输入：`order_no` + `tx_hash` + `amount_units`（最小单位）；可信会话/商户凭据校验同上。
- 状态机：`pending → submitted`（待核验，**不自动 confirmed / 不发权益**；confirmed 仅由链上核验写入）。
- 异常：订单终态重复回执 / 已过期晚到账 / 少付多付 / 缺金额 → 写 `payment_order_exceptions`（order_no/reason/tx_hash/created_at）并将订单置 `exception`（可审计，不自动发权益）。
- 过期：`expire_stale_orders` 活动订单超时 → `expired`，金额槽位释放可复用；旧转账（晚到账）不能匹配新复用金额（按订单快照归属，进异常）。
- 入口：`ultima_backend.payments.api.submit_receipt_endpoint(db, order_no=, tx_hash=, amount_units=, token=, merchant=, api_key=)`。

## 10. UGP-18 服务端链上真实性核验契约（C4 ChainEvidence）

### 核验入口（唯一可推进到账状态）
- `ultima_backend.payments.verification.verify_receipt(intent, chain, provider_result, db=None, tracker=None, now=None)` → `(ChainEvidence|None, status, reason)`；`status ∈ confirmed / pending / rejected`。
- `intent`：`{order_no, receive_address, amount_units, network, created_at, contract|mint|asset_key}`（服务端权威库回）。
- 硬核对：资产（chain+network+contract/mint 定位，**同名伪资产拒绝**）、链/网络、收款方（EVM/TRON `to` 精确、SOL `ata_for`==收款地址）、精确金额（最小单位整数相等，非浮点模糊）、交易成功状态、订单时间窗（早于订单创建超 60s 拒绝）、交易事件唯一性（tx_hash 已绑定其他订单拒绝）。
- 深度门：TRON≥19 / EVM(ETH/BSC)≥12（depth 缺失/不足 → `pending` 待更多确认，不 rejected）；SOL 按最终性（confirmationStatus confirmed/finalized）。
- 连续确认：`ConfirmationTracker` ≥4 轮，每轮必须是有间隔的新观察（block 前进 + 时间前进）；block 回退/重组 → 撤回候选；RPC timeout/null/失败/未知结果不得推进成功。

### 逐链原始响应解析器
- `chains/tron.py parse_trc20_event(raw, contract_hint)`、`chains/evm.py parse_evm_log(raw, contract_hint, chain)`、`chains/solana.py parse_solana_tx(raw, mint_hint)`：输入 provider 原始响应（dict），输出归一化证据字段；关键字段缺失/非 Transfer/失败交易 → ValueError（明确拒绝）。
- 约束：先录制回放与测试网验证；**真实资金、主网地址和链操作仅在专门授权的最终验收任务执行**。`fetch_*_incoming`/`poll_and_settle` 原可信判定替换接线点登记至 UGP-19（落账层消费 ChainEvidence）。

## 11. UGP-19 落账、可靠事件和回调恢复契约

### 落账（原子）
- `ultima_backend.payments.settlement.record_verified_payment(db, order_no, evidence, callback_url=None, now=None)` → `(result, reason)`，result ∈ recorded / duplicate / order_not_found / state_not_active。
- 同事务：`payment_ledger` 写证据（**tx_hash 唯一 = 链事件唯一约束**）→ `payment_orders` → `confirmed`（仅 pending/submitted/confirming 活动态可推进，`source='live'`）→ outbox 入队 PaymentVerified；**网络回调不得夹在数据库事务中**。
- 幂等：同一 tx_hash / 同订单同事件类型重放 → duplicate，不重复入账/入队。

### 事件 outbox 与回调
- `payments/outbox.py`：`enqueue_event`（event_id 唯一，`UNIQUE(order_no,event_type)`）、`claim_events`（到期可领：pending 或 failed 且退避到期、attempts<max）、`mark_delivered` / `mark_failed`（有界重试：10s·2^(n-1) 退避，超 max → dead）。
- `payments/callbacks.py deliver_callbacks(db, secret, batch, http_post, now)`：载荷携带 `event_id` + `signature`（HMAC-SHA256(secret, event_id|order_no|payload)），接入方必须按 event_id 幂等；失败进重试/死信，**回调失败 ≠ 未到账**（订单 confirmed 不回滚）。
- `fulfillment_status(db, order_no)`：`payment_status` / `callback_status` / `fulfillment` 三分——**confirmed 不等于权益已开通**；业务未处理 → `pending`，回调失败/dead → `retry_required`；`done` 由 UGP-27 权益消费写入（本阶段不展示权益已完成）。
