# 05-验收规范 · UltimaRadar

> 定义 DoD（Definition of Done）分层、验收封闭原则与变更流程。所有开发活动按此验收，不达标不算完成。

## 一、DoD 分层

| 层级 | 完成定义 | 验收门 |
|---|---|---|
| 任务级（T 项） | 代码改动 + 单点验证（该功能真实生效） | 对应 verify_*.py 或实测 |
| 工单级（阶段） | 工单任务表全部完成 + 阶段验收通过 | reports/ 审计记录 + 交付验证文档 |
| 阶段级（M1/M2…） | 端到端链路（walking skeleton）跑通 | 重启实测 + 页面验收 |
| 项目级 | 全部功能正常 + 文档/治理闭合 | 治理体检报告 PASS |

## 二、验收封闭原则

1. **实测优先**：功能必须真实运行验证（重启后端/前端，看真实数据），文件存在/语法通过/接口 200 不等于完成。
2. **数据真实**：验证用真实数据（链上/DexScreener/新闻），不 mock；无法取真实数据的明确标注。
3. **回读校验**：生成产物（文档/图表/页面）用与生成路径不同的方式回读检查（如 node --check、curl 实查、日志核对）。
4. **反证检查**：主动找反证——查日志报错、跨页数据一致性、参数冲突，而不只验证预期路径。
5. **闭环留痕**：每阶段验证结果落 reports/ 或 docs/delivery-verification-*.md，可追溯。

## 三、验证工具（scripts/）

- `scripts/verify_*.py`（20+ 个）：各功能专项验证（top10/addr/paper/p3/ui 等）
- `tests/`（3 个 pytest 模块，15 用例）：解析/评分/事件单测
- 运行：`python -m pytest tests/` + 各 `verify_*.py`

## 四、变更流程

1. 需求/方案定案 → 落 docs/ 专项方案 + 08-流程清单登记
2. 拆工单 → tasks/工单-阶段X.md（范围冻结/任务表/总验收/DoD 四段）
3. 开发执行 → 代码产出
4. 验证 → verify 脚本 + 重启实测
5. 审计 → reports/审计-*.md
6. 产物归档 → artifacts/<版本>/

> 变更权限：涉及参数基线（04）取值、DB 表结构、API 契约的变更须同步更新对应文档并复检；写死参数改动须在 14-ADR 登记。
