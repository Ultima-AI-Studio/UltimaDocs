# 项目强制范式标准（Ultima Agent Governance）

- **版本**：v1.7 · 2026-10-16
- **性质**：强制（MUST），高于任何单任务指令与个人习惯；本文件不是建议（SHOULD）
- **适用范围**：所有人类开发者与 AI 代理（含任务执行器、CodeX 类代理）

## 1. 总则

1. 所有写入操作必须落在任务声明域内（见 M2）。
2. 所有开发/立项前必须先查能力注册表（见 M1）。
3. 所有任务完成必须带回执与验收证据（见 M5）。
4. 违反强制规则的产出视为无效，由审计闸门生成修正任务，不静默容忍。

## 2. 强制机制（10 条）

### M1 能力 / 组件注册表（防重复开发）

- **规则**：立项或开发前，必须先读 `docs/specs/registry.md`，确认无现有组件/能力覆盖该需求；任务卡 acceptance 必须包含"已查注册表，无重复"声明。
- **触发点**：新建任务、新建 package、新建组件。
- **违反后果**：任务不得进入 QUEUED；已发生的重复开发，由审计生成"去重合并"修正任务，重复产物移入 `legacy-topo` 或删除（经确认）。

### M2 任务 fileDomain 写入域约束（防存错地方）

- **规则**：每个任务卡必须声明 `fileDomain`（允许写入的绝对路径域，如 `execution/server/...`）；执行器与 AI 代理只允许在声明域内写文件，越界写入视为该任务失败。
- **触发点**：任务派发、代理执行任何写操作。
- **违反后果**：越界写入立即失败；审计记录偏差并生成修正任务，清理/搬回越界文件。

### M3 范式冻结区只读（防规范被随意改）

- **规则**：`docs/paradigms/` 为冻结区，默认只读；修改或新增范式必须走"范式变更流程"（见第 4 节），评审通过后由授权人执行。
- **触发点**：任何对 `docs/paradigms/` 的写入。
- **违反后果**：写入被拒绝；未评审的改动回滚并审计留痕。

### M4 审计一致性检查（防乱放 / 重复悄悄积累）

- **规则**：每轮审计必须核对三件事：
  1. 产物实际路径 vs 任务声明 fileDomain；
  2. 新 package/组件 vs 能力注册表（是否重复）；
  3. logs 报告完整性（summary.json / 回执是否存在）。
  发现偏差 → 生成修正任务。
- **执行工具（挂接 project-governance-audit skill）**：工程级治理体检/审计按 `project-governance-audit` skill 执行——输入工程根目录，对照基准清单（通用 18 项 + AI/Agent 6 项）输出缺口矩阵报告（P0 必建缺失 / P1 不一致 / P2 可选项），附修复建议与修正工单。范式定义"查什么"，Skill 定义"怎么查"。
- **触发点**：定期审计轮（如 S3 章程式）、任务完成时、接手/开工前治理体检。
- **违反后果**：审计不通过的任务不判 COMPLETED；偏差进入修正队列。

### M5 DoD 强制回执（防假完成）

- **规则**：任务完成必须回执：
  1. 产出文件路径列表；
  2. 验收证据（测试结果 / 截图 / 运行日志）；
  3. acceptance 逐项核对结论。
  无回执不判 COMPLETED。
- **触发点**：任务提交完成。
- **违反后果**：状态保持 EXECUTING/BLOCKED；审计生成"补齐回执"修正任务。

### M6 单一现行版本（防旧版本混入现行区）

- **规则**：`execution/` 现行源码区任何时刻只保留**一个现行开发版本**；旧版本、历史快照、worktree、备份目录一律不得进入现行区。
- **触发点**：版本落盘、备份、还原、分支合并。
- **违反后果**：现行区出现旧版命名（`v0rX`、`worktree`、`backup`、`-old`、`copy` 等）→ 审计生成修正任务，移入归档区；不静默容忍新旧混放。
- **覆盖链登记（I5）**：任何"被 ~r1/v1 等新版本覆盖"的任务，原任务自动登记 ARCHIVED 并记录覆盖链（如 `network-channel-v0 → v1`），覆盖关系写入该任务回执，防历史丢失、防覆盖无痕。
- **文档版（M6-DOC，2026-10-16 全局引用）**：M6 同样适用于 **docs 正文区**——每份文档 = 一个版本/一个主题的当前权威：
  1. **跨版本/跨主题必须新开文件**，禁止把新计划追加进旧文件（如新版本计划写入旧 roadmap）；
  2. **更新三步一体**：① 先升头部版本号 → ② 改正文（旧内容移入变更日志）→ ③ 登记变更日志；禁止"新段落追加在旧段落后面、头部版本没动"；
  3. **正文只描述当前版本状态**，旧内容唯一去处是变更日志（即历史归档）；
  4. **三处一致性强制**：头部版本号 = 变更日志最新行 = 正文状态，三者必须一致；不一致即缺陷，审计轮教训扫描（M10）强制检出并生成修正任务。
  - 完整细则见 `docs/specs/version-plan-spec.md` §5.1（文档新旧隔离纪律）。
  - **违反后果**：文档新旧混放 / 三处不一致 → 审计生成修正任务（按 M10-② 教训扫描检出）；不静默容忍。

### M7 版本归档物理隔离（防误改误引用旧版）

- **规则**：历史版本只存 `legacy-topo/versions/`（只读归档区，含迁移来的 Top 快照与 Ultima 自身历史版本），与 `execution/` **物理隔离**；现行代码引用旧版必须**显式声明**（写明路径 + 版本号 + 用途），禁止依赖"文件自然可见"的隐式混用。
- **触发点**：创建归档、引用旧代码。
- **违反后果**：归档区被写入、或现行代码未显式引用即混用旧版 → 审计修正并留痕。

### M8 版本标识与产物归档（防无版本散放）

- **规则**：每个 package / 产物必须携带版本标识（VERSION 文件或包元数据）；构建产物按版本归档 `execution/artifacts/<version>/`；**无版本号的散放产物视为无效**。
- **触发点**：构建、发布、产物落盘。
- **违反后果**：无版本产物 / 版本标识不一致 → 审计生成修正任务补齐或归档。

### M9 守护器运行纪律（Watchdog/调度器，Top watchdog 复盘固化）

> 来源：`docs/reports/watchdog-management-review-20261016.md`（A1/B3/C1/C2/D1/D2 + 自清理边界）+ 2026-10-16 主脑讨论（C3 生命周期绑定）。守护器/调度器（watchdog、派发器、探活器、监控器）统一遵守以下纪律，防"瞎干活"。

- **A1 能力边界**：守护器**只回写任务库状态**，**禁止启停产品进程**（宿主/Brain/WebView2/daemon）；对产品进程只有观察权，无控制权。
- **B3 暂停开关**：守护器必须支持人工熔断——存在暂停标记文件（如 `.pause-dispatch`）时只读审计、不修正、不派发；暂停是治理冻结的标准手段。
- **C1 单实例 + 心跳 + guard 三件套**：任何常驻守护器必须——① 用文件锁实现单实例（防多开重复派发）；② 定期写心跳文件（ts+pid）；③ 配独立 guard 检查心跳过期（如 >600s）则杀旧进程重启；guard 自身也用单实例锁防多开。
- **C2 幂等防重派**：派发前三重判定（派发进程在跑 / 执行会话在跑 / 有活跃 run → 本轮不派）；**探测失败默认按"忙"处理，宁可不派也不重派**。
- **C3 生命周期绑定（防孤岛，2026-10-16 主脑讨论固化）**：守护器**必须是主脑/宿主的子进程**，不得独立常驻、不得脱离父进程存活——
  1. 守护器记录父 pid，每轮探测父进程存活；
  2. **父进程死亡（被杀死/崩溃/正常退出）→ 守护器立即降级只读静默**：停止一切写操作（不回写任务库、不派发、不修正），写入"父进程失联 at <ts>"标记，然后优雅退出；**禁止无主自治**（父死后继续按旧状态机干活）；
  3. 正常关闭顺序固定为：**先停守护器，再退主脑**（父→子顺序，禁止反序）。
  4. 孤儿探测失败一律按"父失联"处理，不得当作"忙"继续干活。
- **D1 状态迁移三纪律**：自动改任务库状态前必须——① 先存档旧状态与日志（如 `runs/stale-recovery/<时间戳>/`）；② 双重确认执行器空闲且任务库未变；③ 才原子替换。任一确认失败即放弃迁移。
- **D2 锁清理**：所有锁（派发锁/实例锁）带过期回收策略：持锁 pid 不活跃或超时（如 3600s）→ 自动清理，防锁残留永久卡死。
- **自清理边界（关键哲学）**：守护器**自清理状态垃圾，不清理文件垃圾**——
  1. **状态级自愈（自动）**：僵尸 EXECUTING 任务（run 日志 ≥30 分钟无更新且无执行会话）→ 转 FAILED 走修正重试（≤2 次）；超时任务（>3600s 且执行器空闲）→ 有证据转 BLOCKED 待审计 / 无证据转 QUEUED 重派；过期锁自动删除。
  2. **文件级保守（不自动删）**：run 日志、done.json、历史产物**永不自动删除**——只忽略、只存档（stale-recovery）；删除不可逆，文件清理交给人工/定期策略。
  - 违反 = 守护器擅自删除文件或擅自启停产品进程 → 审计留痕并生成修正任务。

### M10 教训持续捕获（防"想不起来的坑"，2026-10-16 主脑讨论固化）

> 背景：靠"事后回忆+总结"必然有盲区（未知的未知）。经验不靠总结产生，靠**登记**产生——让坑在发生当下被接住，而不是漏到未来。落点：`docs/references/lessons-log.md`（教训库）。

- **① 触发即登记（MUST）**：任何失败 / 返工 / 卡点 / 绕路 / 工具坑 / 超时 / 环境坑，**当场**写入教训库（现象 / 根因 / 规避 / 复发标记），禁止等总结、禁止"下次再说"。
- **② 审计轮强制扫描**：每轮审计必须检查"本轮是否出现新问题类型未登记"；无新问题也写"范围内未见"（沿用报告口径，不把"未检查"写成"未发现"）。
- **③ 复发检测**：新问题先查教训库——已登记 = 复发（标复发 N 次，深挖根因是否已彻底解决）；未登记 = 新类型（登记 + 评估是否需升级为范式）。
- **④ 维度兜底扫描**：按固定维度表逐格检查，每格要么"已覆盖"要么"待捕获"——不依赖记忆枚举。维度：执行质量 / 治理机制 / 产品交互 / 环境基建 / 工具链 / 数据备份 / 协作交接 / 安全合规 / 性能资源 / 人因认知。
- **⑤ 教训⇄范式双向联动**：教训升级为范式必须走 M3 变更流程；范式新增条目必须回填对应教训条目（双向可追溯）。

## 3. 目录写入权矩阵

| 目录 | 允许写入者 | 说明 |
|---|---|---|
| `docs/paradigms/` | 仅范式变更评审通过后的授权人 | 冻结区，只读 |
| `docs/plans/` | 产品决策人 | 规划文件 |
| `docs/specs/` | 范式对应实现负责人 | 技术规格（含 registry.md） |
| `docs/references/` | 调研执行者 | 调研与借鉴 |
| `tasks/` | 任务执行器 / 立项人 | 任务库与任务卡 |
| `execution/<fileDomain>` | 任务持有者（仅限声明域） | 源码与产物（只保留现行版本） |
| `execution/artifacts/<version>/` | 构建执行者 | 按版本归档的产物（无版本散放无效） |
| `logs/` | 执行器 / 审计 | 运行日志与报告（自动写入） |
| `legacy-topo/` | 迁移授权人 | 只读经验库（迁移后） |
| `legacy-topo/versions/` | 迁移授权人 | 只读版本归档区（Top 快照 + 历史版本） |

## 4. 范式变更流程

1. **提出**：写变更说明（变更理由、影响面、旧版归档方式）。
2. **评审**：主脑 / 产品决策人确认是否放行。
3. **执行**：授权人写入；旧版移入 `docs/paradigms/archive/`。
4. **留痕**：变更记录追加到本文件第 6 节"变更日志"。

## 5. 完成定义（DoD）检查清单

- [ ] 产物落在声明 fileDomain 内
- [ ] 版本标识齐全，产物归档到 `artifacts/<version>/`，现行区无旧版本混入（M6/M8）
- [ ] 能力注册表已更新（新 package/组件已登记）
- [ ] 回执含产出路径 + 验收证据 + acceptance 逐项核对
- [ ] 日志与执行报告已落 `logs/`
- [ ] 无越界写入、无未评审范式改动
- [ ] 任务卡状态与 tasks.json 一致

## 6. 违反处理

- 越界写入 / 重复开发 / 无回执 → 审计生成修正任务（重试上限 2 次，超限转 BLOCKED）。
- 旧版本混入现行区 / 无版本散放 → 移入 `legacy-topo/versions/` 归档并留痕。
- 范式区未评审改动 → 回滚 + 审计留痕。
- 本文件自身变更：必须经产品决策人确认，版本号 +1。
