# 验收规范（Acceptance Spec）

- **版本**：v1.3 · 2026-10-16
- **性质**：范式文件（强制，对应 dev-conductor 05-验收规范；与 project-governance M8 DoD 配套，本文为可执行版）
- **核心**：验收即边界——验收清单是封闭清单，全绿即完成，禁止就地追加；清单外发现 = 新需求走变更流程

## 1. DoD 分层完成定义

| 粒度 | 完成定义（全部满足才算合格） |
|---|---|
| 任务级 | ①"写什么"全部落地 ②验收清单逐项全绿 ③零编译错误零警告 ④未触碰清单外代码 ⑤提交规范（M6） |
| 工单级 | ①全部任务通过 ②总验收通过 ③关联文档同步（docs/README 权威清单）④冻结基线标记 |
| 阶段级 | ①该阶段所有工单通过 ②验收 checklist 逐项打勾 ③下阶段前置核验（环境门） |
| 项目级 | ①全阶段通过 ②总验收清单通过 ③发布包可交付 ④范围清单逐项核对无遗漏（capability-list） |

## 2. 验收封闭原则（强制）

- 验收清单 = 边界；验收时**不得追加新需求**。
- 清单外发现 = 新需求：登记（docs/plans 或 capability-list 缺口）→ 新工单 → 后续阶段实施，**不就地膨胀**。
- 与范式冲突的验收项一律无效，先走变更评审（M3）。

## 3. 验证要求（可能失败的动作）

- **AI 自证 ≠ 完成**：证据必须粘贴（回执含 reviewReason/stdoutText/evidence/acceptance），禁止"预计通过"。
- **独立审计视角**：开发不自证清白——由独立实例/架构师对照验收项反推改动清单复核。
- **真实验证**：跑构建/测试/真实入口，查看渲染结果，抽样重算关键数据；文件存在/非空/语法通过 ≠ 正确。
- **回归**：改过生成逻辑后重跑全部产物；验证通过才标记完成。

## 4. 报告口径（强制）

1. 时间分列：每个事项标时间，不混口径。
2. 未见写"范围内未见"：不得把"未检查"写成"未发现"。
3. 验收按真实口径：页数/字数/条数逐项实数，与需求口径一致。
4. 旧责任列待处理：不抹除历史责任。
5. 决策仅列未裁决项：已裁决的直接写结论。

## 5. 验收流程（四步）

```
① 自检（执行方：对照验收清单逐项自证 + 证据粘贴）
② 复核（独立视角：反推改动清单，对照清单核验）
③ 结论（通过 / 需修改[缺陷打回修复后重验] / 不通过[走变更或废弃]）
④ 归档（验收记录写入该任务回执；冻结标记）
```

## 6. 执行红线（强制，Top 阶段教训固化）

以下三条红线是"人肉审计"固化为"机器闸 + 人工抽检"的可执行版（对应分析报告 I1~I3）：

1. **完成定义三件套（I1）**：任何任务标 COMPLETED 前必须同时满足——
   ① 回执含明确完成语；
   ② 落地文件清单（ADD_FILE / MODIFY_FILE / NEW_FILE 前缀，或 diff --git 记录）；
   ③ 验收证据（测试/构建/运行输出，如 tsc --noEmit、SMOKE_PASS、测试 PASS）。
   三件套缺任一 → 不判 COMPLETED，留主脑审计（UNCLEAR/BLOCKED）。
2. **勘察/实施分离红线（I2）**：勘察或规划完成后**必须进入实施**，禁止停在确认点等待回复（禁止"请回复确认"式收尾）；勘察结论（发现/风险/建议）必须落盘为勘察报告文件，不得只停留在对话。
3. **失败回执结构化（I3）**：失败回执必须包含——① 失败命令/动作 ② 错误原文 ③ 根因判断 ④ 下一步计划；缺一不可重派，禁止只写"失败"二字。
4. **判定 fail-closed（B1，Top watchdog 复盘固化）**：自动化判定只处理**证据明确**的 PASS/FAIL；证据不充分（回执缺失、验收证据不全、进程/日志状态存疑）→ 一律判 UNCLEAR/BLOCKED 留主脑审计，**绝不猜测性判 PASS**。宁可慢，不可错；把"不确定"上浮给人工，是自动系统的第一美德。

> 派发侧：以上红线随每次任务派发由 dispatch 注入 goal（DISCIPLINE_REDLINES）；审计侧：主脑按三件套抽检。

## 7. 结果反推法（验收制定标准，MUST）

> 验收不是"任务写完后补的"，而是**开工前从最终结果反推出来的**。本方法适用所有开发任务（方案制定 → 下发 → 验收全链路），是任务队列拆解的强制起点。

**四层反推**：每一层先定"要什么结果"，再往下拆；拆出来的每一份都有明确验收判据。

```
L4 项目最终结果（成功信号：闭环率/覆盖度/越界拦截/诚实边界）
  ▼ 反推
L3 工单结果（每张工单 = 版本里程碑 + 版本 DoD + 冻结 tag）
  ▼ 反推
L2 任务结果（每个任务 = 验收 Gate + 禁止项）
  ▼ 反推
L1 单元结果（每个单元 = 写什么 + acceptance 逐项 + 证据列）
```

两条强制校验：
1. **完整性**：每层子结果之和 = 父结果（不遗漏）——拆完逐层核对无缺口。
2. **可验证**：每层结果必须有 Gate（不写空话）——没有验收判据的结果无效，打回重定。

**形态**：一单元一卡一验收——每单元一张任务卡，卡内嵌该单元 acceptance（执行依据）；验收对照清单（如 tasks/acceptance-checklist.md）是全部单元的聚合视图（审计依据）。同一份标准两种形态，内容一致不重复。

## 8. 提交前自核闭环（CodeX 义务，MUST）

> 验收标准随任务卡一起下发（goal + acceptance 逐项）；执行方**必须自核通过后才提交回执**，把返工成本消化在执行侧，避免"提交 → 主脑打回 → 再改"的循环。

1. 执行完成后，对照任务卡 acceptance 逐项自核；任一未绿 → 先自修（≤2 次）→ 再自核。
2. 自核全绿才提交回执三件套（I1：完成语 + 落地文件清单 + 验收证据）。
3. **自核不豁免主脑独立审计**（§3 独立审计视角，防自证清白）——自核到位可把打回率压到最低，但审计闸门始终存在。

## 9. 执行 Skill 引用

- **验收/下发/拆解的执行标准**：`engineering-standard` skill（结果反推 → 工程下发 → 工程验收三步；含任务卡模板与验收对照清单模板）。
- 范式（本文件）定义"是什么"与红线；Skill 定义"怎么做"。改 Skill 不改范式，改范式必须走 M3 变更流程。
