# 工程推进流程管理（Project Flow）

- **版本**：v1.4 · 2026-10-16
- **性质**：范式文件（冻结区，变更走评审）；与 governance M1–M8、skill-dispatch 共同生效
- **核心**：每个任务从立项到收尾走固定七阶段；每阶段有明确执行项、产出、门禁与**推理强度**

## 1. 任务生命周期（七阶段）

```
① 立项 Intake → ② 规划 Plan → ③ 派发 Dispatch → ④ 执行 Execute
→ ⑤ 自检 Self-check → ⑥ 审计 Audit → ⑦ 收尾 Close
```

| 阶段 | 做什么 | 具体执行项 | 产出 | 推理强度 | 门禁（进入下一阶段条件） |
|---|---|---|---|---|---|
| ① 立项 Intake | 需求转任务 | 解析 goal → 查能力注册表（M1，确认无重复）→ 写任务卡：goal/acceptance/category/skill/fileDomain/复杂度/reasoningEffort → 入队列 | 任务卡 + QUEUED | **low** | 任务卡字段齐全（缺声明不派发） |
| ② 规划 Plan | 拆解与定口径（仅 M/L 复杂度） | 步骤分解 → 依赖分析（dependsOn）→ 验收口径定义 → 风险识别 | 执行计划附于任务卡 | **high / ultra** | 计划评审通过（L 复杂度需主脑/架构确认） |
| ③ 派发 Dispatch | 路由选技能 | 按 skill-dispatch 规则匹配技能 → 写派发日志（logs/runs）→ 状态 EXECUTING；**随卡下发验收标准**（任务卡内嵌 acceptance，执行依据） | 派发日志 | **low** | 技能匹配成功，一次一主 |
| ④ 执行 Execute | 按技能流程产出 | 读相关范式/规格 → 在声明 fileDomain 内产出 → 版本标识（M8） | 源码/产物 | **medium / high / ultra**（默认 high，见第 3 节） | 产物落声明域 |

> **工程开发执行标准（MUST，挂接 engineering-standard skill）**：③④⑤⑥⑦ 全链路执行细则统一按 `engineering-standard` skill 落地——③ 随卡下发 goal+acceptance（一单元一卡）、⑤ 提交前自核闭环（未全绿先自修 ≤2 次再交回执）、⑥ 主脑独立审计（防自证清白）、⑦ 回执三件套收口。范式定义"是什么"，Skill 定义"怎么做"。

> **I4 长任务分段上报（强制）**：预计超过约 15 分钟的任务，执行过程中必须在派发日志分段写进度（如"已抓取完成 / 正在排序 / 正在编译 / 正在自检"），每段一行；全程静默无进度 = 审计视为卡死候选。60 分钟超时由派发脚本处理，超时任务记录并在下轮重派，不阻塞、不并发。
>
> **B2 串行闸门（强制，watchdog 复盘固化）**：存在 FAILED/BLOCKED 任务且其 base 没有 QUEUED 修正任务（~rN）或 COMPLETED 修正（已通过）时，**禁止派发任何后续任务**——失败未修正不推进（serial gate）。修正排队或已通过后才解除闸门。违反 = 派发器违规并发推进，审计回退并生成修正任务。
>
> **B3 环境门前置（强制，单元级模拟 F1 修正）**：依赖"运行时就绪"证据（单测全绿 / 派发日志 / 端到端运行等运行型产出）的单元，任务卡 dependsOn[] 必须显式前置环境门任务（如 `s1-host-shell-envcheck`）；目录树 / grep / 代码核对类静态产出单元不强制。派发器派发运行型单元前检查环境门状态，**未就绪不派发**。技术栈口径（阶段一）：队列引擎为脚本实现，**仅需 Python 运行时（.NET 维度不适用）**；Python 运行时就绪为全局隐性前置，立项核对须显式声明。后续阶段技术栈变化时更新本口径。
| ⑤ 自检 Self-check | 技能自查 | 编译/测试/核对 acceptance 逐项 → 补回执草稿 | 自检结果 | **medium** | 自检通过 |
| ⑥ 审计 Audit | 独立复核 | 产物路径 vs fileDomain、重复检测 vs 注册表、回执完整性、版本一致性（M4）→ PASS 或生成修正任务 | 审计结论 | **medium** | PASS 才收尾；否则回 ④ 修正（重试 ≤2） |
| ⑦ 收尾 Close | 落盘归档 | 回执定稿（产出路径+证据+acceptance 核对）→ 注册表回填（M1）→ 报告落 logs/execution-reports → COMPLETED/ARCHIVED | 回执 + 报告 | **low** | 回执齐全 |

## 2. 推理强度档位（reasoningEffort）

| 档位 | 适用 | 说明 |
|---|---|---|
| `low` | 机械执行：分类、落盘、回执、检索、派发 | 规则化，不消耗深度推理 |
| `medium` | 规则+轻判断：自检、审计核对、简单实现 | 验证与例行判断 |
| `high` | 主体工程产出：代码、UI、方案实现（默认档） | 任务卡未声明时默认 high |
| `ultra` | 高影响/跨技能/架构级：范式变更、平台迁移、核心引擎、L 复杂度规划 | 需主脑/架构评审背书 |

## 3. 推理强度分配规则

1. **默认 high**：任务卡未声明 `reasoningEffort` 时按 high 执行。
2. **按阶段覆盖**：规划阶段可提升至 ultra，派发/收尾强制 low——推理预算花在"想对方向"，不浪费在"机械搬动"。
3. **任务卡显式声明**：立项时按复杂度预填，L 复杂度默认 ultra（规划）+ high（执行）。
4. **审计核对**：审计轮核对"实际推理档位 vs 任务卡声明"是否一致，偏差记录留痕（不判失败，仅提示）。

## 4. 复杂度 → 流程选择

| 复杂度 | 流程 | 说明 |
|---|---|---|
| S（单步） | ①→③→④→⑤→⑥→⑦ | 跳过规划，直派 |
| M（多步） | 全流程 | 带规划 |
| L（跨技能） | 全流程 + 组合技能 + 评审 | 规划 ultra，执行后强制独立审计 |

## 5. 与现有机制衔接

- 任务卡字段：`category`、`skill`、`fileDomain`、`reasoningEffort`、`dependsOn`、`parallelGroup`（沿袭 Top schema）。
- 状态机：QUEUED → EXECUTING → COMPLETED / FAILED / BLOCKED；修正任务 `~rN` 重走 ④⑤⑥。
- 阶段门禁由执行器强制：未过门禁不进入下一阶段（与 M2/M5 同层强制）。
