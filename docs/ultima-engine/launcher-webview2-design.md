# TuppoGame 登录器正式版设计方案（WebView2 主版本）v1.5

> 方案日期：2026-10-04（v1.1 定稿）→ 2026-10-07（v1.5 合并定稿）
> 方案对象：登录器桌面端（17 §8.1.1i + 17C），将 `web/launcher-prototype/launcher.html` 三层原型 1:1 还原为正式桌面应用
> 版本沿革：v1.1 原稿 → v1.4（云端完善草案，含技术栈对比/圆角/双通道等补充）→ **v1.5 合并定稿**：技术栈回归并确认 **C++ 壳 + WebView2**（渲染效果由 WebView2 内核决定，C++/C# 无差异；C++ 与引擎同栈，授权/协议/发布全链路复用）；用户拍板：圆角窗口、980×820 客户区（整窗即画布）、授权独立签发、Evergreen、仅 Win10/11、stable/beta 双更新通道
> 结论一句话：正式登录器 = **C++ 壳 + WebView2 宿主**，**视觉 100% 复用原型 + 逻辑桥接改造**；原生层承担窗口（无边框圆角）/授权/启动/网关/数据/存储/更新七类能力；L0-L2 最小闭环，启动默认直入第二层（游客模式，跨过账号体系）；更新支持自动（启动检查）+ 手动（设置入口）双通道在线更新，分 stable/beta 通道。

## 1. 还原目标与硬约束

| 项 | 约束（v1.5 已拍板） |
|---|---|
| 窗口 | **无边框圆角窗口**（圆角与设计稿一致），**980 × 820 CSS 像素为客户区尺寸，整窗即设计稿画布**，无系统标题栏/边框/菜单，**不在画布外加任何边框/占用**；禁用系统缩放/最大化 |
| 圆角实现 | Win11：DWM 圆角偏好（`DWMWA_WINDOW_CORNER_PREFERENCE`，系统圆角+系统阴影）；Win10：WebView2 透明背景（`SetDefaultBackgroundColor(Transparent)`）+ 页面自身绘制圆角背景，窗口四角透明（P0 验证项，见 §3） |
| UI 还原 | launcher.html 及 assets/ 视觉资产 100% 复用（扫光/呼吸灯/跑马灯/轮播/弹窗/toast/平滑滑块全部保留）；**逻辑层按桥接改造清单接入原生能力**（见 §4.3） |
| 启动状态 | 正式版启动**默认直入第二层游戏库**（logged 等价态）；第一层登录/注册/找回密码弹窗在正式版隐藏（账号体系后置）；个人信息显示本地游客档案 |
| 系统支持 | 主版本仅 **Win10 / Win11**（WebView2 **Evergreen**，不用固定版）；Win7 兼容版**不立项**（后置独立发布项，暂不评估） |
| 授权语义 | **商家授权随包、独立签发**：登录器校验"商家授权文件 + 自身完整性"，非玩家身份校验；与 M2 共用同一 RSA 体系与代码库但**不同签发实体**（M2=服务器证书，登录器=商家授权包），**不与引擎证书共用**；跳过账号体系不产生矛盾 |
| 更新通道 | **stable / beta 双通道**：设置弹窗可切换；更新检查按当前通道拉取对应 manifest |
| 开发方式 | 分阶段开发、每模块单元测试、用户负责顶层架构/时序/核心代码审查；工具链维持 C++/CMake + Codex，不引入 .NET 等第二套工具链 |

## 2. 总体架构

```
TuppoLauncher.exe（C++ 壳，单 EXE）
├── AppCore       窗口 980×820 无边框圆角 / 生命周期 / 单实例 / DPI / 默认二层启动
├── WebView2Host  虚拟主机映射加载 UI（app.local → 资源目录）+ 桥注入（页面脚本执行前）+ 透明背景（Win10 圆角）
├── NativeBridge  JS ↔ C++ 双向桥（白名单来源校验）
├── Auth          商家授权文件（独立签发）+ RSA 校验 + 登录器完整性自检（与 M2 同体系、不同签发实体）
├── Gateway       与 M2 网关握手（复用阶段6 CommandMessage/加密协议，登录器为发起方）
├── GameLaunch    拉起游戏客户端 + 启动状态机（成功判定 = 客户端回连信号）
├── Net           服务器列表/状态 HTTP 客户端（闭环期本地配置+探测，L3 起接 Web API）
├── Store         本地持久化（设置/昵称/头像文件/金币/两步验证开关）
└── Updater       自动+手动在线更新（manifest 校验 + 哈希/签名验证 + 重启替换；stable/beta 双通道）
```

分层原则：**UI 层只做展示与交互，一切原生能力必须经桥调用**；UI 资产与原生层解耦。

## 3. 窗口与 UI 还原细节

- 窗口：`WS_POPUP` 无边框，**客户区 980×820** 固定（整窗即画布，不加任何外框）；禁用系统缩放/最大化；Per-Monitor V2 DPI，按缩放系数放大整窗（保持画布物理尺寸正确）。
- **圆角窗口（v1.5 新增拍板项）**：
  - **Win11（主目标）**：`DWMWA_WINDOW_CORNER_PREFERENCE = DWMWCP_ROUND`，系统级圆角 + 系统投影；P0 核对系统圆角半径与设计稿是否一致（原型画布圆角约 10~14px 量级），若系统圆角偏小，则 Win11 也走 Win10 的透明背景方案；
  - **Win10**：WebView2 透明背景 + 页面自身绘制圆角深色背景，四角透明；窗口 `WS_EX_LAYERED` 不做（分层窗口与 WebView2 合成有 airspace 兼容风险），改用 WebView2 `SetDefaultBackgroundColor(Transparent)` + DComp 合成（P0 验证项）；
  - **阴影**：跟随系统（Win11 DWM 阴影）；不做自定义分层阴影（避免与 WebView2 合成冲突）。
- 窗口控制：右上角缩小/关闭 → 桥 `win.minimize()` / `win.close()`。
- 窗口拖动：`WM_NCHITTEST` 将 tophead 品牌区映射为 `HTCAPTION`，按住品牌区拖动；HTML 内不做 JS 拖动。
- 单实例：第二实例唤醒已运行进程并置前。
- **资源加载**：`SetVirtualHostNameToFolderMapping` 将资源目录映射为虚拟 host `https://app.local/`；绕开 file:// 的 fetch/XHR 限制（L3 接 HTTP 顺畅），资源目录可独立更新。
- **桥注入时序**：`AddScriptToExecuteOnDocumentCreated` 在页面任何脚本执行前注入 `window.tuppoNative` 骨架，避免原型代码首次运行即 undefined。

## 4. 桥协议

### 4.1 JS → 原生

| 方法 | 参数 | 返回 | 说明 |
|---|---|---|---|
| `win.minimize()` | — | — | 最小化窗口 |
| `win.close()` | — | — | 关闭窗口 |
| `auth.check()` | — | `{ok, code, msg}` | 商家授权（独立签发）+ 完整性校验（启动时） |
| `server.getList()` | — | `[Server]` | 服务器列表（区/名/版本/标签/状态/在线/开服时间） |
| `server.getStatus(id)` | — | `{status, online}` | 单服实时状态 |
| `game.launch({gameId, serverId, token})` | — | `{ok, code}` | 发起启动（进入状态机） |
| `store.get(key)` / `store.set(key,val)` | key,val | value / ok | 持久化（头像/昵称/设置/金币） |
| `update.check({auto, channel})` | auto:bool, channel | `{current, latest, hasUpdate, url, size}` | 检查更新（auto=启动静默 / 手动=设置入口；channel=stable/beta） |
| `update.apply()` | — | — | 下载并安装更新（返回进度回调） |
| `user.*` | — | — | 账号体系占位（账号中心对接后启用） |

### 4.2 原生 → JS（回调）

| 回调 | 载荷 | 驱动 |
|---|---|---|
| `onLaunchProgress` | `{stage, pct, msg}` | 第三层启动动画（检测→授权→握手→拉起→回连） |
| `onServerStatus` | `{id, status, online}` | 列表实时在线人数/状态（L3+） |
| `onAuthInvalid` | `{code, msg}` | 授权/完整性失效 → UI 弹窗 |
| `onUpdateProgress` | `{pct, stage}` | 更新下载/校验/安装进度 |
| `onUpdateResult` | `{ok, code, msg}` | 更新完成/失败 → UI 提示（完成则提示重启） |

### 4.3 原型桥接改造清单（逻辑层接入点）

| 原型动作 | 现状 | 改造为 |
|---|---|---|
| 右上角缩小/关闭 | 纯 UI | `win.minimize()` / `win.close()` |
| 第三层"进入游戏" | toast 演示 | `game.launch(...)` + 订阅 `onLaunchProgress` 驱动启动动画 |
| 个人设置头像上传/昵称保存 | localStorage | `store.set('avatar')/store.set('uname')`（头像落文件） |
| 设置弹窗保存（语言/记住登录） | 内存变量 | `store.set('lang')/store.set('rmb')` |
| 设置弹窗**更新通道切换（stable/beta）** | 无 | 新增选择项 → `store.set('channel')` + 提示切换后下次检查生效 |
| 两步验证开关 | localStorage | `store.set('twofa')` |
| 版本号展示 | 静态 V1.2.0 | `version` → `update.check` 结果 |
| 设置弹窗"检查更新"入口 | 无 | 新增按钮 → `update.check({auto:false, channel})` |
| 更新提醒弹窗 + 底部进度条 | 无 | updateMask 弹窗 + updateBar 底部进度条（原型已实现；正式版由 `onUpdateProgress`/`onUpdateResult` 驱动） |
| 启动检测（环境检测弹窗） | 前端假检测 | L2 起接原生检测（客户端完整性/运行库/WebView2） |
| 登录/注册/找回密码弹窗 | 完整流程 | 正式版隐藏（账号体系后置），保留代码位 |

### 4.4 桥安全

- 仅 `https://app.local/` 源可调用桥方法（来源白名单校验）；页面内 XSS 不能乱调 `win.close`/`store`/`update.apply`。
- 原生→JS 回调统一 marshal 到 UI 线程派发。

## 5. 启动状态机（第三层"进入游戏"）

```
选服 → 进入游戏
  ├─ 检测环境（客户端完整性 / 运行库 / WebView2）
  ├─ 授权校验（商家授权文件 + 完整性，失效→onAuthInvalid）
  ├─ 网关握手（超时→提示重试）
  ├─ 拉起客户端（传 gameId/serverId/token）
  └─ 回连确认（客户端连接网关回执）→ 进入游戏
失败分支：维护中（不可进入）、拥挤（排队提示）、握手超时、授权失效、客户端缺失、回连超时
```

**成功判定**：以客户端回连网关的回执信号为准（非进程启动即成功）；回连超时视为失败并提示。

## 6. 授权对接（商家授权随包 · 独立签发）

- 登录器校验**商家授权文件**（随包分发，商家购买 M2 授权后配套**独立签发**）+ 自身完整性（复用阶段8 TamperCheck 思路）。
- 与 M2 共用同一 RSA 体系与代码库，但**签发实体不同**：M2 校验服务器证书，登录器校验商家授权包（独立证书/密钥对签发，**不与引擎证书共用**）；玩家无需账号/设备注册即可启动（游客模式成立）。

## 7. 网关握手对接（复用阶段6）

- 复用 CommandMessage 编解码 + 加密流程，登录器为握手发起方。
- 无账号模式下 `token` 由网关按游客/设备上下文签发（占位阶段先传演示值，语义在 L2 实现期冻结）。

## 8. 数据源分级

| 阶段 | 服务器列表/状态数据 | 在线人数口径 | 说明 |
|---|---|---|---|
| L0-L2 最小闭环 | 本地配置 + 启动探测 | **静态占位（标注演示）** | 不依赖网络 |
| L3 | 登录器 → Web API（HTTP） | 真实数据 | 契约与后台共用（见 §15 排期） |
| 后续 | 实时推送（onServerStatus） | 实时 | WebSocket/长轮询，后台阶段定 |

**依赖标注**：L3 依赖外部服务层（Web 端+后台）详细设计——审计结论该层详细设计缺失；**按 §15 排期：契约先行（33-对外API契约规范），L3 启动前契约必须定稿**，避免契约无源。

## 9. 本地持久化（Store）

- 键值（settings.json，`%APPDATA%/TuppoGame/launcher/`）：昵称、语言、记住登录、两步验证、金币余额、筛选偏好、**更新通道 channel**，键名沿用 `tg_*`。
- **头像单独存文件**（`%APPDATA%/.../avatar.<ext>`），settings.json 只存路径，避免 base64 膨胀 JSON。
- 授权信息不入本地明文存储。

## 10. 更新机制（自动 + 手动在线更新 · stable/beta 双通道）

### 10.1 触发通道（两种更新模式）

**① 用户确认更新（普通更新）**
- **自动检查发现**：登录器启动时静默检查，发现新版 → **弹出更新提醒弹窗**（当前版本 → 新版本 + 更新内容摘要 + 取消/立即更新）→ 用户确认后开始下载。
- **手动检查**：设置弹窗"关于"区"检查更新"入口 → `update.check({auto:false, force:false, channel})`；无新版 toast"已是最新版本"；有新版 → 同样弹出更新提醒弹窗。
- 进度条含"取消"（用户自己发起的更新可取消），取消不影响当前版本。

**② 后台强制更新**
- 登录器启动**先检测**（`update.check({auto:true, force:true})`）；发现强制更新 → **无需确认直接更新**，进度条正常拉取 → 完成后自动重启登录器。
- 强制模式**不显示取消按钮**，不可中断；适用于必须升级的场景（安全补丁/协议变更/版本下线）。

**进度反馈（两种模式共用）**：登录器**最底侧显示更新进度条**（下载 → 校验 → 安装分阶段文案 + 百分比）。

### 10.2 更新通道（v1.5 新增）

| 通道 | 用途 | 切换入口 |
|---|---|---|
| stable | 正式版，默认 | 设置弹窗"关于"区 |
| beta | 预发布/灰度 | 设置弹窗"关于"区（切换后下次检查生效，toast 提示） |

- 通道由 `store.set('channel')` 持久化；`update.check` 按当前通道拉取对应 manifest；
- beta 通道可见 beta 版本；stable 通道仅见正式版本；强制更新（force=true）无视通道，任何通道都必须执行。

### 10.3 更新清单（manifest）

| 字段 | 说明 |
|---|---|
| `channel` | 所属通道（stable / beta） |
| `version` | 最新版本号（语义化） |
| `force` | 是否强制更新（true=强制，无需用户确认；false=普通，弹窗确认） |
| `files[]` | 变更文件清单（路径 + SHA256 哈希）——复用阶段9 哈希清单方案 |
| `url` | 更新包下载地址（HTTPS） |
| `size` | 更新包大小 |
| `signature` | 更新包签名（发布密钥 RSA 签名，防中间人篡改） |

### 10.4 更新流程

```
【用户确认更新】
检查（auto/manual，按 channel 拉 manifest）→ 比对版本 → 有新版（force=false）：弹出更新提醒弹窗（用户确认）
  → 确认：底部进度条（可取消）下载 → SHA256 校验 → RSA 签名校验 → 校验失败即中止（不安装）
  → 暂存到 %APPDATA%/.../update/（进度条：安装阶段）→ 提示重启 → 替换 EXE + 资源 → 校验后启动新版本

【后台强制更新】
启动检测（force=true，无视通道）→ 比对版本 → 有强制新版：无需确认直接更新
  → 底部进度条（无取消）下载 → SHA256 校验 → RSA 签名校验 → 校验失败即中止（保持旧版本运行）
  → 暂存到 %APPDATA%/.../update/（进度条：安装阶段）→ 自动重启 → 替换 EXE + 资源 → 校验后启动新版本
```

- 失败处理：网络失败/校验失败 → 提示稍后重试，**不影响当前版本使用**；签名或哈希不通过绝不安装。
- 更新范围：登录器本体（EXE + UI 资源）；玩家客户端版本管理不在自更新范围（由 L2 客户端完整性检测另管）。

## 11. 打包（L6）

- 单 EXE + 资源目录随包分发（虚拟主机映射加载，资源目录可独立更新）。
- 图标/版本资源/数字签名复用阶段9 发布流程；更新包单独 RSA 签名。
- 发布时 stable / beta 各打一套包与 manifest，版本号强一致注入。

## 12. 工单拆分与里程碑

| 工单 | 内容 | 验收要点 |
|---|---|---|
| L0 壳骨架 | 980×820 **无边框圆角**窗口（Win11 DWM 圆角 / Win10 透明背景+页面圆角，含 P0 圆角方案验证）、虚拟主机映射加载 UI、**桥注入（脚本执行前）**、单实例、win.minimize/close、tophead 拖拽、DPI、**默认直入二层 + 游客档案 + 登录弹窗隐藏** | 原型 UI 壳内 1:1 呈现（无 file:// 限制报错），桥骨架存在且来源白名单生效；四角圆角与设计稿一致，Win10/11 双机验证 |
| L1 授权接入 | 商家授权文件（独立签发）+ RSA 校验 + 完整性自检 + onAuthInvalid | 无授权包/被篡改时拦截进游戏（单测覆盖） |
| L2 启动链路 | 启动状态机 + game.launch + 拉起客户端 + 网关握手 + **回连成功判定** | 第三层"进入游戏"全流程走通，含回连超时等失败分支 |
| L3 数据接入 | server.getList/getStatus + Net 客户端（**前置：Web API 契约设计，见 §15**） | 列表/状态/在线人数真实数据源 |
| L4 持久化 | store 桥 + 设置/昵称/**头像文件**/通道落盘 | 重启后状态恢复（含 channel 保持） |
| L5 自更新 | update.check（auto/manual + force 双模式 + **stable/beta 通道**）+ 更新提醒弹窗 + 底部进度条 + manifest + 下载/校验 + 重启替换 + 设置弹窗"检查更新"/通道切换入口 | 新旧版本切换成功；篡改包拒绝安装；普通更新可取消、强制更新无确认无取消，交互与原型一致；通道切换生效 |
| L6 打包发布 | 单 EXE + 资源 + 图标签名 + 更新包签名 + stable/beta 双包 | 发布包可运行，签名/哈希校验通过 |

**里程碑**：L0-L2 = 最小闭环（选服→进入游戏真实可用 + 启动更新静默检查）；L3-L6 后置；Win7 兼容版 = 不立项（主版本稳定后再评估）。

## 13. 开发约束

- 沿用项目规范：分阶段开发，单阶段验收通过冻结后再进下一阶段；每模块附带单元测试。
- 编码：Codex 高级订阅分模块编码/单测/编译调试；用户负责顶层架构、时序规则、核心代码（Auth/GameLaunch/Gateway/Updater）审查。
- 工具链：**维持 C++/CMake + 现有构建体系**，不引入 .NET 等第二套工具链。
- UI 资产维护：launcher.html 原型为设计真源，样式/逻辑迭代在原型完成，构建时从原型同步资产；**原型逻辑桥接改造（§4.3）随 L0 一并落地**。

## 14. 边界与风险

| 风险 | 对策 |
|---|---|
| WebView2 运行时缺失（精简系统） | 启动检测 + 引导安装 Evergreen；列入环境检测 |

## 17. 游戏包结构与安装规范（Beta 通道，2026-10-08 用户拍板）

> 背景：Beta 通道"静默预下载 + 卡片状态流转"已闭环（下载→落盘→卡片彩色→开始游戏）；真实客户端尚未整理，**本版仅定结构与安装约定**，解压实现随客户端就绪落地。用户拍板：安装目录 = **启动器同目录 `Games\<game_id>\`**，启动器自动引导。

### 17.1 目录结构（磁盘约定）

```
<TuppoLauncher.exe 所在目录>\
├── TuppoLauncher.exe
├── ...（登录器自身资源目录，随包）
└── Games\                      ← 安装根（与登录器同目录，首次安装时自动创建）
    ├── mir\                    ← 热血传奇（game_id = mir）
    │   └── <客户端文件…>         ← zip 解压内容直接落此
    ├── mu\                     ← 奇迹 MU（game_id = mu）
    └── <game_id>\              ← 后续游戏同构
```

- 安装根取 **`GetModuleFileNameW` 的 exe 目录**，非 `%LOCALAPPDATA%`（packs 缓存留在 LocalAppData，游戏本体随登录器同盘同目录，便于用户整体搬迁/清理）。
- `%LOCALAPPDATA%\TuppoGame\packs\<game_id>.zip` 仅作**下载缓存**；安装完成后保留（支持重装/覆盖更新时免下载），由后台策略决定是否清理。

### 17.2 zip 包结构约定（R2 上传规范）

- 上传位置：R2 桶 `tuppo-launcher`，键 `packs/<game_id>.zip`（现网 `https://update.sellerrule.com/packs/mir.zip`）。
- **zip 根目录直接为客户端根，不含顶层 `<game_id>` 文件夹**（例：zip 内第一层即 `Mir.exe`、`Data/`…，而非 `mir/Mir.exe`）。
  - 理由：解压 = 直接展开到 `Games\<game_id>\`，无需剥层判断；所有游戏统一此约定，后台/登录器零特判。
- 包元数据存 D1 `game` 表：`pack_url` / `pack_size` / `pack_version`（已建）；**新增 `launch_exe`**（相对 `Games\<game_id>\` 的主程序路径，如 `Mir.exe` / `Client.exe`；后台可配，避免各游戏主程序名不统一）。

### 17.3 安装流程（状态机扩展）

```
game.download（已有）→ 下载到 packs 缓存
  → 完整性校验：pack_size 比对（SHA256 待 add，同更新闭环校验位）
  → 解压到 Games\<game_id>\（覆盖式：先删旧 Games\<game_id>\ 再展开，防残留脏文件）
  → store 写 tg_install_<game_id> = Games\<game_id>\（替换旧 L1 约定）
  → 前端卡片转"开始游戏"（现有 finishDownload 事件，无需改动 UI）
```

- **启动引导**：`game.launch` 读 `tg_install_<game_id>` + `launch_exe`（后台下发时随包信息缓存本地）→ 拼 `Games\<game_id>\launch_exe` 绝对路径 → 原参数协议不变（`-game <id> -server <zone> -name "<name>"`）。旧约定 `<game_id>_client.exe` 作废。
- **游戏包更新**：启动时/进入游戏前比对 `pack_version`（本地 store `tg_packver_<id>`）≠ 后台 → 后台静默重下覆盖；沿用卡片状态流转（灰→下载中%→可玩），不弹确认。

### 17.4 解压实现选型（P0 待定，随客户端就绪落地）

| 方案 | 说明 | 取舍 |
|---|---|---|
| A. minizip（zlib 附带） | vcpkg 加 `zlib` 依赖，C API 解压，可控进度 | 推荐：纯 C++、可报进度/条目数、与现有工具链一致 |
| B. Shell COM（Shell.Application CopyHere） | 系统自带，无新依赖 | 慢、难报进度、异步完成难等；仅作兜底 |
| C. 内置 inflate | 手写 zip 读取 + inflate | 工作量大、维护成本高；不选 |

**默认选 A**；进度/百分比沿用现有 `game.download.progress` 事件通道（解压阶段 `stage:"unzip"`）。
