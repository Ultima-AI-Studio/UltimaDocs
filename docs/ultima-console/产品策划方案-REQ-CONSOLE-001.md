# Ultima Console 产品策划方案 · REQ-CONSOLE-001

- 版本：v0.2（已拍板）｜ 日期：2026-10-17 ｜ 状态：待 Codex 审计 → 冻结
- 上游：REQ-CONSOLE-001（需求已登记）｜ 下游：技术落地方案（审计冻结后启动）

## 一、问题

Owner 管理多个 AI 开发产品，进度、工单、审计、文档散落在本地 / GitHub / 飞书，没有一屏看清全部产品状态、进度、评分与偏移的监督入口，监督靠翻聊天和文件。

## 二、为谁

| 画像卡 | 内容 |
|---|---|
| 画像 1：Owner（产品持有者/拍板人） | 情境：日常在电脑端与豆包/DeepSeek 沟通开发，碎片时间用鸿蒙平板查看全局。要完成的进展：不用开电脑、不翻对话，一屏看清每个产品"到哪了、好不好、有没有偏移、下一步该拍什么板"。现在的凑合方案：翻聊天记录 + 逐个开 GitHub/本地文件 + 飞书文档。痛点：信息散、无状态汇总、决策缺依据、离线/关机时看不到。 |
| 画像 2：协作者（Codex/DeepSeek 执行端） | 情境：执行端被派发任务后需要回执落盘。要完成的进展：按统一制式上报结果，不依赖沟通记忆。现在的凑合方案：各自写文件、格式不一。痛点：无统一回执标准、审计要人工核对。 |

## 三、竞品与替代品

定位图（两轴：监督深度 × 上手成本）：
- 自己（Ultima Console）：高监督深度 / 低上手成本——为"多 AI 产品私有监督"定制，只出结果
- Jira / 禅道：高监督深度 / 高成本——重流程，面向团队，无 AI 多端私有场景
- 飞书多维表格 / 项目：中监督深度 / 中成本——通用，需自建字段，无审计评分
- 自建 Dashboard（Grafana 等）：中监督深度 / 高成本——面向指标，不面向产品文档/工单/审计语义

功能对比矩阵（0-2 打分：0 无 / 1 弱 / 2 强）：

| 功能维度 | Ultima Console | Jira | 飞书项目 | 自建看板 |
|---|---|---|---|---|
| 多产品一屏监督 | 2 | 1 | 1 | 1 |
| 只出结果不显示过程 | 2 | 0 | 0 | 0 |
| 工单→审计→评分闭环 | 2 | 1 | 0 | 0 |
| 多通道（A/B 双执行端） | 2 | 0 | 0 | 0 |
| 本地/GitHub/飞书三源读取 | 2 | 0 | 1 | 1 |
| 鸿蒙平板原生+旋转 | 2 | 0 | 0 | 0 |
| 上手成本 | 低 | 高 | 中 | 高 |

替代品分析（JTBD 视角）：用户现在"拿什么凑合"= 翻聊天记录 + 开文件 + 手动记状态；本产品替代为"打开平板即见全局"。

## 四、主流程旅程（一条主流程：打开→看全局→钻取→拍板）

| 阶段 | 用户动作 | 触点 | 情绪 | 痛点 | 机会 |
|---|---|---|---|---|---|
| 打开 | 启动 APP，看四板块仪表盘 | 平板主屏 | 期待 | 之前要翻多个地方 | 一屏给全局状态 |
| 概览 | 扫产品状态/评分/偏移/阻塞 | 仪表盘卡片 | 安心/警觉 | 数字无解释会焦虑 | 关键指标 + 小助手摘要 |
| 钻取 | 点产品 → 看规划/阶段/工单/审计 | 二级页逐层 | 清晰 | 层级太深会迷路 | 左侧导航 + 右侧内容联动 |
| 拍板 | 看小助手建议 → 审核 → 同意/打回 | 审批视图 | 果断 | 缺决策依据 | 建议 + 影响分析一起给 |
| 闭环 | 指令反馈回文档库/GitHub | 后台静默 | 放心 | 担心没闭环 | 回执状态可见 |

## 五、功能范围

### P0（Must，本期必做——没有则系统不成立）
- F1 四板块仪表盘：沟通规划中 / 开发中 / 已开发结束 / 已上线（REQ-CONSOLE-001）
- F2 产品级钻取：规划/介绍 → 阶段状态 → 工单列表 → 审计报告 → 项目进度（REQ-CONSOLE-001）
- F3 任务/工单逐层展开：任务计划 → 任务单元 → 执行版本/阶段 → 工单审计（REQ-CONSOLE-001）
- F4 评分评估：推进评分、偏移判定、偏移纠正、问题清单（REQ-CONSOLE-001）
- F5 数据链路读取：本地（权威源）→ GitHub（桥接）→ 飞书（灾备/授权连接可选）（REQ-CONSOLE-001）
- F6 鸿蒙原生 + 可旋转：横屏双栏（左导航右内容）/ 竖屏独立布局（REQ-CONSOLE-001）
- F7 只出结果：统一标准制式，不显示沟通过程（REQ-CONSOLE-001）
- F8 小助手（审核/总结/建议/关键节点汇报）：经用户同意反馈文档库，形成闭环（REQ-CONSOLE-001）

### P1（Should，重要，纳入 MVP 不砍）
- P1-1 双通道可视化：A/B 通道产品分栏标识与切换（REQ-CONSOLE-001）
- P1-2 审批流：方案生成 → 小助手总结 → 用户审核 → 同意/打回（REQ-CONSOLE-001）
- P1-3 偏离预警：达到回滚/偏移阈值时主动提示（REQ-CONSOLE-001）

### P2（Could，锦上添花）
- P2-1 市场运营内容板块：产品介绍/文案/物料展示（REQ-CONSOLE-001）
- P2-2 版本对比视图：历史版本/回滚记录可视化（REQ-CONSOLE-001）
- P2-3 多端同步进度（iOS/Mac/安卓/Windows 端状态一览）（REQ-CONSOLE-001）

### 本期不做（Won't，明确排除）
- W1 不做任务派发/编辑（只监督 + 审核 + 下达指令）
- W2 不做聊天对话界面（不显示沟通过程）
- W3 不做多语言国际化（首版仅中文）
- W4 不做 Windows/iOS 原生端（鸿蒙跑通定型后第二阶段同步）
- W5 不做账号体系与多人协作（单 Owner 私有）

## 六、成功标准

```
北极星：Owner 每周主动打开查看产品的次数 ≥ 5 次（监督成为习惯）
  基线：0（现无产品）  目标：≥5 次/周  时间窗：上线后 4 周
输入指标：
- 全局状态一屏可读（四板块产品数 / 卡壳数 / 待拍板数）
- 钻取深度达标率：点产品后 3 步内到达工单/审计层 ≥ 90%
- 决策闭环率：小助手建议 → 用户拍板 → 反馈落盘的回执率 ≥ 80%
- 评分与偏移数据新鲜度：≤ 1 天延迟（随 GitHub 桥接同步）
- 只出结果原则：界面 0 显示沟通过程（验收时抽查）
护栏：
- 不牺牲"只监督"边界（不偷偷加编辑/派发能力）
- 不牺牲离线可用性（断网时仍可读取最近一次有效状态，不白屏）
- 不牺牲标准制式（各产品必须按 sync 规范供数，不做特例）
工期说明：本产品开发全部交由 Codex 执行，完成时间无法预估，**不设工程工期预算**；进度以工单 DoD/验收门为准，不以日历天数为约束。
```

## 七、MVP 边界与版本规划

MVP 闭环（验证最危险假设）："Owner 能否在平板上 3 步内看清任一产品的状态、工单、审计、评分与偏移"——假设风险最高的是"数据链路能否自动同步 + 制式回执是否齐"。

MVP 范围（P0+P1 全纳入，不砍）：F1-F8（四板块 + 钻取 + 工单展开 + 评分 + 数据链路 + 鸿蒙旋转 + 只出结果 + 小助手）+ P1-1/P1-2/P1-3（双通道可视化 + 审批流 + 偏离预警）。开发交由 Codex 执行，以功能完成度与 DoD 验收为完成标准，不设日历工期。

版本规划（Now-Next-Later，挂可衡量结果不挂功能名）：

| 桶 | Theme | 对应 | 可衡量结果 |
|---|---|---|---|
| Now | 监督仪表盘 MVP（鸿蒙） | REQ-CONSOLE-001 | 四板块 + 产品钻取 + 工单/审计可见 + 评分偏移显示 + 双通道分栏 + 审批流 + 偏离预警 |
| Next | 数据链路与回执自动化 | REQ-CONSOLE-001 | 本地/GitHub 自动同步 ≤1 天；回执率 ≥80% |
| Later | 多端同步 + 运营板块 | REQ-CONSOLE-001 | iOS/Mac/安卓/Windows 端状态一致；运营内容页上线 |
